## 内存模型

### JVM的内存模型

<div align="center"> <img src="https://oss.javaguide.cn/github/javaguide/java/jvm/java-runtime-data-areas-jdk1.8.png" width="75%"/> </div>

JVM的内存结构主要分为以下几个部分：

- **程序计数器**：可以看作是当前线程所执行的字节码的行号指示器，用于存储当前线程正在执行的 Java 方法的 JVM 指令地址。如果线程执行的是 Native 方法，计数器值为 null。是唯一一个在 Java 虚拟机规范中没有规定任何 OutOfMemoryError 情况的区域，生命周期与线程相同。

- **Java 虚拟机栈**：每个线程都有自己独立的 Java 虚拟机栈，生命周期与线程相同。每个方法在执行时都会创建一个栈帧，用于存储局部变量表、操作数栈、动态链接、方法出口等信息。可能会抛出 StackOverflowError 和 OutOfMemoryError 异常。

- **本地方法栈**：与 Java 虚拟机栈类似，主要为虚拟机使用到的 Native 方法服务，在 HotSpot 虚拟机中和 Java 虚拟机栈合二为一。本地方法执行时也会创建栈帧，同样可能出现 StackOverflowError 和 OutOfMemoryError 两种错误。

>**概念上**，Java 虚拟机栈服务 Java 方法，本地方法栈服务 Native 方法；
>**实现上**，在 HotSpot 虚拟机中**两者合二为一**，你可以认为它们没有区别。

- **Java 堆**：是 JVM 中最大的一块内存区域，被所有线程共享，在虚拟机启动时创建，用于存放对象实例。从内存回收角度，堆被划分为新生代和老年代，新生代又分为 Eden 区和两个 Survivor 区（From Survivor 和 To Survivor）。如果在堆中没有内存完成实例分配，并且堆也无法扩展时会抛出 OutOfMemoryError 异常。
- **方法区（元空间）**：在 JDK 1.8 及以后的版本中，方法区被元空间取代，使用本地内存。用于存储类元数据（类的结构信息、方法字节码、字段信息）、运行时常量池（Class 文件中的常量表）等。而字符串常量池和静态变量实际存储在堆内存中。虽然方法区被描述为堆的逻辑部分，但有 “非堆” 的别名。MaxMetaspaceSize = 稳定占用 × 2，如果元空间达到 `-XX:MaxMetaspaceSize` 上限，且 GC 后仍无法释放足够内存，会抛出`java.lang.OutOfMemoryError: Metaspace`。
- **运行时常量池**：是方法区的一部分，用于存放编译期生成的各种字面量和符号引用，具有动态性，运行时也可将新的常量放入池中。当无法申请到足够内存时，会抛出 OutOfMemoryError 异常。
- **直接内存**：不属于 JVM 运行时数据区的一部分，通过 NIO 类引入，是一种堆外内存，可以显著提高 I/O 性能。直接内存的使用受到本机总内存的限制，若分配不当，可能导致 OutOfMemoryError 异常。

> **方法区是 JVM 规范中的逻辑概念，元空间是 JDK 8 及以后对方法区的具体实现。**
> 打个比方：方法区是“接口”，元空间是“实现类”。

JDK 7 及以前：方法区的实现叫**永久代（PermGen）**
JDK 8 及以后：方法区的实现叫**元空间（Metaspace）**

堆与元空间的关系：

1. **堆管"对象实例"**（具体的数据），**元空间管"类定义"**（数据的蓝图）。
2. **堆里的每个对象都知道自己属于哪个类**（通过指针关联到元空间）。
3. **元空间扩容会触发GC**，但GC回收的是堆里的对象，元空间内存只有在该类的所有对象都被回收后才会被释放。





### JVM内存模型里的堆和栈有什么区别？

核心类比：栈 = 办公桌，堆 = 中央仓库

- **栈 (办公桌)**：你正在处理的任务（方法）放在桌上。桌上东西（局部变量）拿取极快，用完立刻丢掉。但桌子面积有限，堆太多文件（递归过深）会塌（`StackOverflowError`）。
- **堆 (中央仓库)**：所有长期保存的物品（对象）都放仓库里。仓库空间巨大，但找东西慢。你需要通过桌上的**物品编号（引用）** 去仓库取。清洁工（`GC`）会定时清理仓库里没人要的垃圾。

1. **用途不同**

- **栈**：存局部变量、方法参数、返回地址。方法调用时创建栈帧，结束则销毁。
- **堆**：存所有 `new` 出来的对象实例和数组。

2. **生命周期不同**

- **栈**：方法结束，栈帧销毁，数据自动消失。
- **堆**：对象存活时间不确定，直到没有引用指向它时，被 GC 回收。

3. **存取速度不同**

- **栈**：快。因为遵循 LIFO（后进先出），CPU 支持度高，只需移动指针。
- **堆**：慢。因为需要动态分配内存、寻找空闲块、处理 GC。

4. **存储空间不同**

- **栈**：空间小且固定（通常几百 KB 到几 MB），容易溢出。
- **堆**：空间大且动态（通常几百 MB 到几 GB），溢出较难但可能。

5. **可见性不同**

- **栈**：线程私有。每个线程有自己的栈，其他线程无法访问。
- **堆**：线程共享。所有线程都能访问堆里的对象。

**总结对照表**

| 维度         | 栈 (Stack)               | 堆 (Heap)            |
| :----------- | :----------------------- | :------------------- |
| **用途**     | 方法调用、局部变量、引用 | 对象实例、数组       |
| **生命周期** | 方法结束即销毁           | 无引用时 `GC` 回收   |
| **存取速度** | 快                       | 相对慢               |
| **空间大小** | 小，固定                 | 大，动态扩展         |
| **管理方**   | 操作系统 / JVM 自动      | JVM（`GC` 负责回收） |
| **线程关系** | 线程私有                 | 线程共享             |
| **溢出错误** | `StackOverflowError`     | `OutOfMemoryError`   |

**一句话总结：** 栈负责**执行**（方法调用和临时变量），快速但短暂；堆负责**存储**（对象数据），缓慢但持久。栈存的是"工作台上的草稿"，堆存的是"仓库里的货物"。



### 栈中存的到底是指针还是对象？

栈里存遥控器，堆里存电视机

- **栈 (Stack)**：存的是**遥控器**（引用/Reference）。遥控器很小（比如 8 个字节），上面写着电视机在仓库的**地址**。
- **堆 (Heap)**：存的是**电视机**（对象实例）。电视机很大，有各种属性（颜色、尺寸、频道）。

严格来说，引用是 JVM 规范定义的抽象概念，但在 HotSpot 等主流 JVM 中，它的实现就是一个指针。

| 概念                 | 通俗理解 | 技术实现 (HotSpot)                             |
| :------------------- | :------- | :--------------------------------------------- |
| **引用 (Reference)** | 遥控器   | 一个 32 位 (4字节) 或 64 位 (8字节) 的内存地址 |
| **对象 (Object)**    | 电视机   | 堆中的一块连续内存，包含对象头、实例数据等     |

在Java中，局部变量（包括基本类型和对象引用）通常存储在栈帧中，而对象实例通常分配在堆中。但在实际JVM实现（如HotSpot）中，经过逃逸分析优化，对象也可能被分配在栈上，甚至被完全消除。

### 堆分为哪几部分

![img](https://miro.medium.com/v2/resize:fit:875/0*rzQ6-DyP-2gjiua7)



| 区域     | 图片中的标注      | 作用                         |
| :------- | :---------------- | :--------------------------- |
| **Eden** | "New Objects"     | 新创建的对象先放这里         |
| **S0**   | "Survivor Spaces" | 幸存者区0（From 或 To）      |
| **S1**   | "Survivor Spaces" | 幸存者区1（From 或 To 互换） |

`Minor GC` 发生在新生代的垃圾回收。

| 参数             | 含义           |
| :--------------- | :------------- |
| `-XX:NewSize`    | 新生代初始大小 |
| `-XX:MaxNewSize` | 新生代最大大小 |
| `-Xms`           | 堆初始大小     |
| `-Xmx`           | 堆最大大小     |

> **注意**：`-Xms` 和 `-Xmx` 控制的是**整个堆**（新生代 + 老年代），不只是老年代。

| 位置                  | 含义                                        |
| --------------------- | :------------------------------------------ |
| 老年代右边的 Reserved | 堆内存中预留的空间，还没实际分配给老年代    |
| 新生代底部的 Reserved | 可能是 S0/S1 中未使用的部分，或预留扩展空间 |

**通俗理解**：JVM 从操作系统申请内存时，不会一下子全占满，而是先申请一个虚拟地址空间（Reserved），然后按需分配（Committed）。这就像你租了一套大房子，但只把要用的房间收拾出来，其他房间先空着（Reserved），以后需要再打开。

**堆 = 新生代（Eden + S0 + S1）+ 老年代**。
**新对象进 Eden → Minor GC 后幸存者进 S0/S1 → 多次幸存后进老年代 → Major GC 回收老年代**
**`-Xms`/`-Xmx` 控制整个堆，`-XX:NewSize`/`-XX:MaxNewSize` 控制新生代**



**Eden = 伊甸园**，是圣经中人类诞生的地方。
JVM 借用这个名字，寓意 **"对象诞生的地方"**。
配合 **Survivor**（幸存者）和 **Old Gen**（老年代），构成了一个完整的"对象生命周期"叙事：**出生 → 幸存 → 老去 → 死亡**。



### 如果有个大对象一般是在哪个区域？

1. 核心策略：大对象直接进老年代

为了避免新生代成为性能瓶颈，JVM 会将**需要大量连续内存的大对象**（如长数组）**跳过新生代，直接在老年代分配**。

2. 三大原因（为什么不进新生代）

- **减少GC频率**：新生代空间小，大对象易占满Eden区，导致频繁触发Minor GC。
- **降低复制开销**：Minor GC采用复制算法，搬运大对象成本极高。
- **避免内存碎片**：新生代分配频繁，大对象易导致内存碎片，进而引发分配失败。

>并非所有大对象都直接进老年代，不同垃圾收集器的策略不同。

| 垃圾收集器                          | 大对象处理策略                                               |
| :---------------------------------- | :----------------------------------------------------------- |
| **Parallel Scavenge**（JDK 8 默认） | 通过 `-XX:PretenureSizeThreshold` 参数控制，超过阈值的大对象**直接进老年代** |
| **G1**                              | 大对象（超过一个 Region 的 50%）进入 **Humongous 区域**（专门的大对象区，属于老年代范畴） |
| **CMS**                             | 支持 `PretenureSizeThreshold`，大对象直接进老年代            |
| **Serial / ParNew**                 | 同样支持该参数                                               |



### 程序计数器的作用，为什么是私有的

程序计数器有两个特点：

1. **记录当前线程执行到哪一条字节码指令**，类似于一个"行号指示器"。

2. **线程私有**的。因为 Java 程序是多线程的，CPU 会不断切换线程执行。当线程被挂起时，需要用它记住执行位置，下次切换回来才能继续。如果所有线程共用一个计数器，切换后就不知道从哪继续执行了。

| 特殊点                             | 说明                                                         |
| :--------------------------------- | :----------------------------------------------------------- |
| **唯一不会 OOM 的区域**            | 程序计数器只需要存储一个地址，容量固定且极小，JVM 规范没有规定它会发生内存溢出 |
| **执行 Native 方法时为 undefined** | Native 方法是 C/C++ 实现的机器码，不是 Java 字节码，所以不需要记录字节码地址 |

### 方法区中的方法的执行过程？ 

方法执行过程分为四个步骤：

1. **解析**：JVM 根据符号引用找到实际方法地址（如果是第一次调用）。
2. **创建栈帧**：在当前线程的虚拟机栈中分配一个栈帧，用于存放局部变量表、操作数栈、动态链接等。
3. **执行**：运行方法内的字节码指令。
4. **返回**：执行完毕，返回结果，弹出当前栈帧，恢复调用者的执行环境。



### 方法区中还有哪些东西？

方法区主要存储 5 类数据：

第一，**类型信息**，比如类的完整结构、父类、接口等；

第二，**运行时常量池**，包括字面量和符号引用；

第三，**静态变量**，也就是 `static` 修饰的类变量；

第四，**方法的字节码**，即编译后的指令；

第五，**JIT 编译后的机器码**，用于缓存热点代码，提升执行效率。

> **JIT** 是 **Just-In-Time Compilation** 的缩写，中文叫**即时编译**。它是 JVM 中一个**极其重要的性能优化技术**。**JIT 会把"热点代码"（反复执行的方法或循环）从字节码编译成机器码，直接交给 CPU 执行，大幅提升运行速度。**



### String保存

String 保存在字符串常量池中，不同于其他对象，它的值是不可变的，且可以被多个引用共享。

| 创建方式                 | 代码示例                          | String 对象存储位置          | 引用是否进入常量池 | 能否共享复用 |
| :----------------------- | :-------------------------------- | :--------------------------- | :----------------- | :----------- |
| **字面量**               | `String s = "hello";`             | 堆（JDK 7+） 永久代（JDK 6） | ✅ 是               | ✅ 是         |
| **new String()**         | `String s = new String("hello");` | 堆（普通对象区域）           | ❌ 否               | ❌ 否         |
| **intern()**             | `s.intern()`                      | 堆（JDK 7+ 可能移入常量池）  | ✅ 是（如不存在）   | ✅ 是         |
| **+ 拼接（编译期确定）** | `"hel" + "lo"`                    | 堆（JDK 7+）                 | ✅ 是               | ✅ 是         |
| **+ 拼接（运行期确定）** | `"hel" + new String("lo")`        | 堆（普通对象区域）           | ❌ 否               | ❌ 否         |



### String s = new String（“abc”）执行过程中分别对应哪些内存区域

执行 `String s = new String("abc");` 时，JVM 做了三件事：

1. **处理字面量 `"abc"`**：
   - 先去**字符串常量池**（JDK 7+ 在堆中）找有没有 `"abc"` 的引用。
   - **如果没有**：在**堆**中创建一个 `"abc"` 的 String 对象，并把它的**引用**放到常量池中。
   - **如果有**：直接拿到常量池中已有的引用。
2. **执行 `new String()`**：
   - 在**堆**中创建一个**新的** String 对象（复制品）。
   - 这个新对象的内容和上面的 `"abc"` 一样，但**身份不同（内存地址不同）**。
3. **赋值**：
   - 将栈中的局部变量 `s` 指向第2步中 `new` 出来的那个 String 对象。





### 引用类型有哪些？有什么区别

| 引用类型   | 实现类                 | GC 回收时机                           | 典型应用场景                                               |
| :--------- | :--------------------- | :------------------------------------ | :--------------------------------------------------------- |
| **强引用** | 默认 (`A a = new A()`) | **永不回收**（宁可OOM）               | 所有常规对象                                               |
| **软引用** | `SoftReference`        | **内存不足时**（OOM前）               | 内存敏感缓存（如图片缓存）                                 |
| **弱引用** | `WeakReference`        | **下次 GC 时**（无论内存是否充足）    | `WeakHashMap`、`ThreadLocal` 中的 `Entry` 的 key           |
| **虚引用** | `PhantomReference`     | **随时**（无法通过 `get()` 获取对象） | 对象回收跟踪、堆外内存释放（如 NIO 的 `DirectByteBuffer`） |

> **一句话记忆**：强引用死也不回收，软引用快死才回收，弱引用见GC就回收，虚引用等于没有引用。



```java
// 1. 强引用：内存不足时直接 OOM，不会回收
Object strongRef = new Object();

// 2. 软引用：内存够就留着，不够就回收
Object softObj = new Object();
SoftReference<Object> softRef = new SoftReference<>(softObj);
softObj = null; // 去除强引用，只剩软引用

// 3. 弱引用：只要 GC 发生，就会被回收
Object weakObj = new Object();
WeakReference<Object> weakRef = new WeakReference<>(weakObj);
weakObj = null;

// 4. 虚引用：必须和 ReferenceQueue 配合
ReferenceQueue<Object> queue = new ReferenceQueue<>();
Object phantomObj = new Object();
PhantomReference<Object> phantomRef = new PhantomReference<>(phantomObj, queue);
phantomObj = null;
// phantomRef.get() 永远返回 null
```



### 弱引用的使用场景

- **缓存系统**：弱引用常用于实现缓存，特别是当希望缓存项能够在内存压力下自动释放时。如果缓存的大小不受控制，可能会导致内存溢出。使用弱引用来维护缓存，可以让JVM在需要更多内存时自动清理这些缓存对象。
- **对象池**：在对象池中，弱引用可以用来管理那些暂时不使用的对象。当对象不再被强引用时，它们可以被垃圾回收，释放内存。
- **避免内存泄露**：当一个对象不应该被长期引用时，使用弱引用可以防止该对象被意外地保留，从而避免潜在的内存泄露。

经典场景：`ThreadLocal` 的内存泄漏预防

这是面试中高频考点。`ThreadLocalMap` 的 `Entry` 源码如下：

```java
static class Entry extends WeakReference<ThreadLocal<?>> {
    Object value;
    Entry(ThreadLocal<?> k, Object v) {
        super(k);  // key 是弱引用
        value = v;
    }
}
```

为什么 key 要用弱引用？

* key 用弱引用，是为了保证 `ThreadLocal` 对象本身不泄漏（能被 GC 回收）。

* 但 value 的泄漏需要程序员主动调用 `remove()` 来避免。

这是一个精妙的权衡：弱引用解决了“根本性泄漏”（key 本身），但把“次级泄漏”（value）的责任交给了开发者，同时提供了 `get/set/remove` 时清理 `null` key 的兜底机制。



### 内存泄漏和内存溢出

**内存泄露**：内存泄漏是指程序在运行过程中不再使用的对象仍然被引用，而无法被垃圾收集器回收，从而导致可用内存逐渐减少。虽然在Java中，垃圾回收机制会自动回收不再使用的对象，但如果有对象仍被不再使用的引用持有，垃圾收集器无法回收这些内存，最终可能导致程序的内存使用不断增加。

内存泄露常见原因：

- **静态集合**：使用静态数据结构（如`HashMap`或`ArrayList`）存储对象，且未清理。
- **事件监听**：未取消对事件源的监听，导致对象持续被引用。
- **线程**：未停止的线程可能持有对象引用，无法被回收。

**内存溢出**：内存溢出是指Java虚拟机（JVM）在申请内存时，无法找到足够的内存，最终引发`OutOfMemoryError`。这通常发生在堆内存不足以存放新创建的对象时。

内存溢出常见原因：

- **大量对象创建**：程序中不断创建大量对象，超出JVM堆的限制。
- **持久引用**：大型数据结构（如缓存、集合等）长时间持有对象引用，导致内存累积。
- **递归调用**：深度递归导致栈溢出。



### jvm 内存结构有哪几种内存溢出的情况？

- **堆内存溢出**：当出现Java.lang.OutOfMemoryError:Java heap space异常时，就是堆内存溢出了。原因是代码中可能存在大对象分配，或者发生了内存泄露，导致在多次GC之后，还是无法找到一块足够大的内存容纳当前对象。
- **栈溢出**：如果我们写一段程序不断的进行递归调用，而且没有退出条件，就会导致不断地进行压栈。类似这种情况，JVM 实际会抛出 StackOverFlowError；当然，如果 JVM 试图去扩展栈空间的的时候失败，则会抛出 OutOfMemoryError。
- **元空间溢出**：元空间的溢出，系统会抛出Java.lang.OutOfMemoryError: Metaspace。出现这个异常的问题的原因是系统的代码非常多或引用的第三方包非常多或者通过动态代码生成类加载等方法，导致元空间的内存占用很大。
- **直接内存溢出**：在使用ByteBuffer中的allocateDirect()的时候会用到，很多JavaNIO(像netty)的框架中被封装为其他的方法，出现该问题时会抛出Java.lang.OutOfMemoryError: Direct buffer memory异常。



### 堆溢出

堆溢出（`java.lang.OutOfMemoryError: Java heap space`）通常发生在程序持续创建对象且无法被 GC 及时回收的场景下。

**定位原因**：

1. **捕获内存快照**：通过 JVM 参数`-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=./heapdump.hprof`，让程序在发生 OOM 时自动生成堆快照文件。
2. **分析快照文件**：使用 MAT（Memory Analyzer Tool）或 JProfiler 等工具分析快照，重点看哪些对象占用了大量内存、是否存在内存泄漏（如对象长期被无用引用持有，无法回收）。

**解决**：分两种情况。

1. **内存泄漏**：对象不该活却活着（如静态 List 缓存）。解决是**切断引用**，比如清空集合或使用 `WeakHashMap`。
2. **内存不足**：对象确实需要那么多。解决是**扩容**（`-Xmx`）或**降需**（分批处理）。



### 栈溢出

栈溢出主要发生在 Java 虚拟机栈（或本地方法栈）的内存空间被耗尽时，通常与方法调用的深度直接相关。

从触发原因来看，最常见的场景是无限递归调用。因为 Java 方法调用时会在栈中创建栈帧（存储局部变量、操作数栈、方法返回地址等），每递归一次就会新增一个栈帧。如果递归没有正确的终止条件，栈帧会不断累积，最终超过虚拟机栈的最大容量，导致栈溢出。

另一种情况是单个方法的栈帧过大。如果一个方法定义了大量局部变量，或者局部变量占用内存过大（比如大数组），单个栈帧就会占用较多栈空间，可能在调用层级不深时就耗尽栈内存。

| 对比维度             | 栈溢出 (StackOverflowError)                | 堆溢出 (OutOfMemoryError: Java heap space) |
| :------------------- | :----------------------------------------- | :----------------------------------------- |
| **发生区域**         | Java 虚拟机栈（或本地方法栈）              | 堆                                         |
| **根本原因**         | 栈帧太多 或 单个栈帧太大                   | 对象太多 或 对象太大，无法被 GC 回收       |
| **典型场景**         | 无限递归、深度递归、超大局部变量数组       | 内存泄漏、加载海量数据、缓存过大           |
| **关键参数**         | `-Xss`（栈大小，默认 1MB 左右）            | `-Xms`、`-Xmx`（堆大小）                   |
| **能否通过调参根治** | 通常不能（只能延缓，递归无限调再大也会爆） | 部分可以（如果是内存不足，扩容有效）       |
| **解决优先顺序**     | 1. 改代码（改递归）→ 2. 调参数             | 1. 查泄漏 → 2. 改代码 → 3. 调参数          |

**注意点：**

* **栈帧大小不是固定的**：局部变量越多、越大，单个栈帧越大，同样深度下更容易栈溢出
* **`-Xss` 是线程级参数**：每个线程有自己的栈，总内存固定时，`-Xss` 越大，能创建的线程数越少（`max_threads ≈ 总内存 / Xss`）
* **某些 JVM 实现会延迟抛出**：HotSpot 并不是精确到栈帧满才抛，而是预留一个"红色区域"，触碰即抛





### 具体的内存泄漏和内存溢出的例子及解决方案

| 错误类型     | 英文             | 本质                                             | 比喻                         |
| :----------- | :--------------- | :----------------------------------------------- | :--------------------------- |
| **内存泄漏** | Memory Leak      | **该回收的对象**被误持有了引用，导致 GC 无法回收 | 水龙头没关紧，**一滴一滴漏** |
| **内存溢出** | OutOfMemoryError | **内存真的不够用了**，无法分配新对象             | 水池满了，**水溢出来**       |

> **关系**：内存泄漏 → 可用内存逐渐减少 → 最终导致内存溢出。**泄漏是原因，溢出是结果**。

#### 案例 1：静态集合导致的内存泄漏（最经典）

```java
public class LeakExample {
    // 静态 List 生命周期 = 整个 JVM 运行期间
    private static List<Object> staticList = new ArrayList<>();
    
    public void addObject() {
        Object obj = new Object();
        staticList.add(obj);  // obj 被静态 List 持有，永远不会释放
    }
}
```

- 每次调用 `addObject()`，`Object` 对象都被 `staticList` 强引用
- 方法结束后，`obj` 局部变量消失，但 `staticList` 还引用着这个对象
- 随着调用次数增加，`staticList` 越来越大，最终导致 OOM

解决方案

```java
// 方案1：用完即清
public void addObjectAndClean() {
    staticList.add(new Object());
    // 业务逻辑...
    staticList.clear();  // 手动清空
}

// 方案2：使用 WeakHashMap 代替普通 Map
private static Map<Object, String> cache = new WeakHashMap<>();

// 方案3：使用带过期策略的缓存（如 Guava Cache、Caffeine）
LoadingCache<String, Object> cache = Caffeine.newBuilder()
    .maximumSize(1000)           // 最大数量
    .expireAfterWrite(10, TimeUnit.MINUTES)  // 10分钟过期
    .build(key -> new Object());
```

#### 案例 2：未关闭的资源（IO 流、数据库连接）

```java
public void readFile(String path) throws IOException {
    FileInputStream fis = new FileInputStream(path);
    // 如果这里抛出异常，fis 永远不会 close
    int data = fis.read();
    // 忘记调用 fis.close();
}
```

- 每次读取文件都会打开一个文件句柄
- 操作系统文件句柄有限，最终导致"Too many open files"
- JVM 层面：`FileInputStream` 对象持有 native 资源，GC 无法回收

解决方案

```java
// 方案1：try-with-resources（JDK 7+，推荐）
public void readFile(String path) throws IOException {
    try (FileInputStream fis = new FileInputStream(path)) {
        int data = fis.read();
    } // 自动 close
}

// 方案2：finally 手动关闭
public void readFile(String path) {
    FileInputStream fis = null;
    try {
        fis = new FileInputStream(path);
        int data = fis.read();
    } catch (IOException e) {
        e.printStackTrace();
    } finally {
        if (fis != null) {
            try { fis.close(); } catch (IOException e) {}
        }
    }
}
```

#### 案例 3：ThreadLocal

**核心原因：Entry 的 key 是弱引用，但 value 是强引用**

```java
// ThreadLocalMap 中的 Entry 源码
static class Entry extends WeakReference<ThreadLocal<?>> {
    Object value;  // 注意：value 是强引用！
    
    Entry(ThreadLocal<?> k, Object v) {
        super(k);  // key 是弱引用
        value = v;
    }
}

public class Service {
    // 静态 ThreadLocal，所有实例共享
    private static ThreadLocal<UserContext> userContext = new ThreadLocal<>();
    
    public void process() {
        userContext.set(new UserContext("user123"));  // 设置值
        // ... 业务处理 ...
        // 忘记调用 userContext.remove()
    }
}
```

| 步骤 | 发生了什么                                           | key (ThreadLocal)                                            | value (UserContext)                          |
| :--- | :--------------------------------------------------- | :----------------------------------------------------------- | :------------------------------------------- |
| 1    | 线程池中线程 T1 执行 `set()`                         | 强引用指向 ThreadLocal                                       | 强引用指向 UserContext                       |
| 2    | 方法执行完毕，但线程 T1 返回线程池（**线程不销毁**） | 局部变量 `userContext` 出栈，ThreadLocal 对象的**外部强引用消失** | —                                            |
| 3    | GC 发生                                              | key 是弱引用 → **被回收**，变成 `null`                       | value 还是强引用 → **无法回收**！            |
| 4    | 结果                                                 | Entry 变成 `key=null, value=UserContext`                     | 这个 Entry 永远无法被访问，但 value 一直存在 |

最终结果

> **Entry 的 key 是 null，但 value 是强引用，卡在 Entry 数组里，线程池的线程永远不死，value 就永远无法被回收 → 内存泄漏！**

解决方案

使用 `try-finally` 保证 `remove()`

```java
public class CorrectUsage {
    private static ThreadLocal<UserContext> userContext = new ThreadLocal<>();
    
    public void process() {
        try {
            userContext.set(new UserContext("user123"));
            // ... 业务逻辑 ...
        } finally {
            userContext.remove();  // 关键：确保移除
        }
    }
}
```







### 对象访问定位的方式有哪些？

建立对象就是为了使用对象，我们的 Java 程序通过栈上的 reference 数据来操作堆上的具体对象。对象的访问方式由虚拟机实现而定，目前主流的访问方式有：**使用句柄**、**直接指针**。

#### 句柄

如果使用句柄的话，那么 Java 堆中将会划分出一块内存来作为句柄池，reference 中存储的就是对象的句柄地址，而句柄中包含了对象实例数据与对象类型数据各自的具体地址信息。

<div align="center"> <img src="https://oss.javaguide.cn/github/javaguide/java/jvm/access-location-of-object-handle.png" width="75%"/> </div>



#### 直接指针

如果使用直接指针访问，reference 中存储的直接就是对象的地址。

<div align="center"> <img src="https://oss.javaguide.cn/github/javaguide/java/jvm/access-location-of-object-handle-direct-pointer.png" width="75%"/> </div>



虚拟机通过栈上的 `reference` 定位到堆上的对象，主流方式有两种：

| 方式             | 实现原理                                                     | 示意图（简化）                                            |
| :--------------- | :----------------------------------------------------------- | :-------------------------------------------------------- |
| **使用句柄**     | 堆中划分一块**句柄池**，`reference` 指向句柄地址，句柄包含对象实例数据指针、类型数据指针。 | `reference` → [句柄] → 对象实例数据        → 对象类型数据 |
| **使用直接指针** | `reference` 直接存储对象地址，对象内存中必须包含类型数据的指针。 | `reference` → 对象实例数据 + 类型指针                     |

简单类比：

- **句柄**：你去政府办事，先找窗口（句柄），窗口告诉你去哪个科室（对象）。科室搬迁，窗口改告示就行，你手上的号不用变。
- **直接指针**：你直接去科室地址。科室搬迁，必须通知所有办证的人换新地址。

### 对象的生命周期

| 阶段       | 核心动作              | 发生区域               | 关键点                                 |
| :--------- | :-------------------- | :--------------------- | :------------------------------------- |
| **① 创建** | `new` + 构造函数      | 堆                     | 分配内存、初始化零值、设置对象头       |
| **② 使用** | 通过引用访问属性/方法 | 栈（引用）→ 堆（对象） | 可能被多个引用指向                     |
| **③ 销毁** | GC 回收               | 堆                     | **无强引用**时成为垃圾，回收时机不确定 |

#### 1. 对象的“复活”可能

> 在销毁阶段，如果对象被 GC 检测到不可达，但在执行 `finalize()` 方法时，又把自己赋值给了某个静态变量或 GC Roots 能引用的对象，那么它就**复活**了。
>
> - **注意**：`finalize()` 已废弃，不推荐使用，但这个机制证明了销毁不是绝对的。

#### 2. 对象的“年龄”概念

> 对象在 GC 中不是一次没被回收就直接进老年代。它在 Survivor 区每熬过一次 Minor GC，**年龄就 +1**，达到阈值（默认 15）才晋升到老年代。

### 类加载过程

类从被加载到虚拟机内存中开始到卸载出内存为止，它的整个生命周期可以简单概括为 7 个阶段：加载（Loading）、验证（Verification）、准备（Preparation）、解析（Resolution）、初始化（Initialization）、使用（Using）和卸载（Unloading）。其中，验证、准备和解析这三个阶段可以统称为连接（Linking）。

系统加载 Class 类型的文件主要三步：**加载->连接->初始化**。连接过程又可分为三步：**验证->准备->解析**。

| **3.生成 Class 对象** | 在堆中创建一个 `Class` 对象      | 作为方法区数据的访问入口                            |

#### 准备

准备阶段是正式为类变量分配内存并设置类变量初始值的阶段，这些内存都将在方法区中分配。

#### 解析

解析阶段是虚拟机将常量池内的符号引用替换为直接引用的过程。 解析动作主要针对类或接口、字段、类方法、接口方法、方法类型、方法句柄和调用限定符 7 类符号引用进行。

#### 初始化

**初始化阶段就是 JVM 自动调用你写的静态变量赋值和静态代码块，把它们真正执行一遍，让类从“准备好了”变成“活起来了”的那一步。**

> **初始化阶段是类加载过程的最后一步，核心是执行 `<clinit>()` 方法。**
>
> 该方法由编译器自动收集类中**所有静态变量的赋值动作**与**静态代码块**合并生成，JVM 会保证其执行时的**线程安全**与**按源码顺序执行**。
>
> 与**准备阶段**仅为静态变量分配内存并赋予默认零值不同，初始化阶段才真正执行程序员期望的赋值逻辑和业务代码，标志着类完成从“加载”到“就绪”的转变。



### 类加载器

#### 定义

- 类加载器是一个负责加载类的对象，用于实现类加载过程中的加载这一步。
- 每个 Java 类都有一个引用指向加载它的 `ClassLoader`。
- 数组类不是通过 `ClassLoader` 创建的（数组类没有对应的二进制字节流），是由 JVM 直接生成的。

#### 类加载器加载规则

JVM 启动的时候，并不会一次性加载所有的类，而是根据需要去动态加载。也就是说，大部分类在具体用到的时候才会去加载，这样对内存更加友好。

对于已经加载的类会被放在 `ClassLoader` 中。在类加载的时候，系统会首先判断当前类是否被加载过。已经被加载的类会直接返回，否则才会尝试加载。也就是说，对于一个类加载器来说，相同二进制名称的类只会被加载一次。

#### 种类

JVM 中内置了三个重要的 `ClassLoader`：

1. **`BootstrapClassLoader`(启动类加载器)**：最顶层的加载类，由 C++实现，通常表示为 null，并且没有父级，主要用来加载 JDK 内部的核心类库（ `%JAVA_HOME%/lib`目录下的 `rt.jar`、`resources.jar`、`charsets.jar`等 jar 包和类）以及被 `-Xbootclasspath`参数指定的路径下的所有类。
2. **`ExtensionClassLoader`(扩展类加载器)**：主要负责加载 `%JRE_HOME%/lib/ext` 目录下的 jar 包和类以及被 `java.ext.dirs` 系统变量所指定的路径下的所有类。
3. **`AppClassLoader`(应用程序类加载器)**：面向我们用户的加载器，负责加载当前应用 classpath 下的所有 jar 包和类。



### 双亲委派模型

<div align="center"> <img src="https://oss.javaguide.cn/github/javaguide/java/jvm/class-loader-parents-delegation-model.png" width="75%"/><p>双亲委派模型</p></div>

`ClassLoader` 类使用委托模型来搜索类和资源。每个 ClassLoader 实例都有一个相关的父类加载器。需要查找类或资源时，ClassLoader实例会在试图亲自查找类或资源之前，将搜索类或资源的任务委托给其父类加载器。虚拟机中被称为 "bootstrap class loader"的内置类加载器本身没有父类加载器，但是可以作为* `ClassLoader` 实例的父类加载器。

- `ClassLoader` 类使用委托模型来搜索类和资源。
- 双亲委派模型要求除了顶层的启动类加载器外，其余的类加载器都应有自己的父类加载器。
- `ClassLoader` 实例会在试图亲自查找类或资源之前，将搜索类或资源的任务委托给其父类加载器。

> **双亲委派模型 = 先找爸爸加载，爸爸找不到，自己再加载。**

就像一个孩子（子类加载器）要找一个玩具（类），他先让爸爸（父类加载器）去找，爸爸再让爷爷去找……如果爷爷辈都找不到，才自己动手。

类加载器之间的父子关系一般不是以继承的关系来实现的，而是通常使用组合关系来复用父加载器的代码。

在面向对象编程中，有一条非常经典的设计原则：**组合优于继承，多用组合少用继承。**

> 这句话的核心是指出继承的脆弱性——它破坏了封装，让子类依赖父类的实现细节。而组合通过委托的方式，让类之间保持松耦合，行为可以动态改变。在实际开发中，我更倾向于优先使用组合，只有在明确的‘is-a’关系、且子类完全符合父类契约时才会考虑继承。一个典型的例子是策略模式，它就是用组合替代继承的经典实践。
>
> 组合提供的“动态性”通常是通过**成员变量 + setter 方法**实现的。





## 垃圾回收

垃圾回收（Garbage Collection, GC）是自动管理内存的一种机制，它负责自动释放不再被程序引用的对象所占用的内存，这种机制减少了内存泄漏和内存管理错误的可能性。垃圾回收可以通过多种方式触发，具体如下：

- **内存不足时**：当JVM检测到堆内存不足，无法为新的对象分配内存时，会自动触发垃圾回收。
- **手动请求**：虽然垃圾回收是自动的，开发者可以通过调用 `System.gc()` 或 `Runtime.getRuntime().gc()` 建议 JVM 进行垃圾回收。不过这只是一个建议，并不能保证立即执行。
- **JVM参数**：启动 Java 应用时可以通过 JVM 参数来调整垃圾回收的行为，比如：`-Xmx`（最大堆大小）、`-Xms`（初始堆大小）等。
- **对象数量或内存使用达到阈值**：垃圾收集器内部实现了一些策略，以监控对象的创建和内存使用，达到某个阈值时触发垃圾回收。

堆中几乎放着所有的对象实例，对堆垃圾回收前的第一步就是要判断哪些对象已经死亡（即不能再被任何途径使用的对象）。



### GC 管理的内存区域

| 内存区域             | 是否被 GC 管理       | 说明                                                         |
| :------------------- | :------------------- | :----------------------------------------------------------- |
| **堆（Heap）**       | ✅ **是（主要目标）** | 存放所有 `new` 出来的对象实例、数组。这是 GC 工作的主战场。  |
| **方法区（元空间）** | ✅ **是**             | 存放类信息、常量、静态变量等。也会发生 GC（如卸载类、回收常量池），但条件苛刻，效果有限。 |
| **程序计数器**       | ❌ 否                 | 只是当前线程执行字节码的行号指示器，几乎不占内存。           |
| **Java 虚拟机栈**    | ❌ 否                 | 每个栈帧中的局部变量表（存放基本类型和对象引用）会随着方法调用自动创建销毁，不需要 GC。 |
| **本地方法栈**       | ❌ 否                 | 同上，为 native 方法服务。                                   |

> **一句话总结：GC 主要管堆，顺便管一点方法区。**



### 垃圾判断算法

#### 引用计数法

给对象中添加一个引用计数器：

- 每当有一个地方引用它，计数器就加 1；
- 当引用失效，计数器就减 1；
- 任何时候计数器为 0 的对象就是不可能再被使用的。、

**这个方法实现简单，效率高，但是目前主流的虚拟机中并没有选择这个算法来管理内存，其最主要的原因是它很难解决对象之间循环引用的问题。**



#### 可达性算法

这个算法的基本思想就是通过一系列的称为 **“GC Roots”** 的对象作为起点，从这些节点开始向下搜索，节点所走过的路径称为引用链，当一个对象到 GC Roots 没有任何引用链相连的话，则证明此对象是不可用的，需要被回收。

**对象并非“非死不可”**

一个对象即便被**可达性分析算法**判定为“不可达”（也就是从GC Roots出发找不到它），它也不会立即被处决，而是进入一个**“缓刑期”**。在这个缓刑期内，对象有机会通过`finalize()`方法完成最后一次自救。这就像法庭审判的“一审”和“二审”：

**第一次标记与筛选**（一审）

- **触发条件**：对象经过可达性分析，发现没有与GC Roots相连的引用链。
- **动作**：JVM会对这个对象进行第一次标记。
- **筛选（是否进入“缓刑”名单）**：判断对象是否有必要执行`finalize()`方法。
  - **情况A（没必要执行）**：对象没有覆盖`finalize()`方法，或者`finalize()`方法已经被JVM调用过了。→ **直接判定死亡**，等待回收。
  - **情况B（有必要执行）**：对象覆盖了`finalize()`方法，且该方法从未被调用过。→ **判定为“有必要执行”**，对象被放入一个叫 **F-Queue** 的队列中，获得“缓刑”。

**第二次标记与真正死亡**（二审）

- **执行**：JVM会创建一个优先级较低的**Finalizer线程**去执行F-Queue队列中对象的`finalize()`方法。
- **动作**：在`finalize()`方法执行完毕后，JVM会对队列中的对象进行**第二次标记**。
- **判决结果**：
  - **自救成功**：如果在执行`finalize()`方法的过程中，对象成功将自己与**GC Roots引用链上的任何一个对象**建立了关联（比如把自己赋值给某个类的静态变量，或者某个还在存活对象的成员变量），那么它就会被移出“即将回收”的集合，**重获新生**。
  - **自救失败**：如果执行完`finalize()`后，对象仍然没有与GC Roots建立关联，那它就会被第二次标记，随后被真正回收。



### GC Roots

- 虚拟机栈(栈帧中的局部变量表)中引用的对象
- 本地方法栈(Native 方法)中引用的对象
- 方法区中类静态属性引用的对象
- 方法区中常量引用的对象
- 所有被同步锁持有的对象
- JNI（Java Native Interface）引用的对象



### 垃圾回收算法有哪些

#### 标记-清除算法

标记-清除（Mark-and-Sweep）算法分为“标记（Mark）”和“清除（Sweep）”阶段：首先标记出所有不需要回收的对象，在标记完成后统一回收掉所有没有被标记的对象。

它是最基础的收集算法，后续的算法都是对其不足进行改进得到。这种垃圾收集算法会带来两个明显的问题：

1. **效率问题**：标记和清除两个过程效率都不高。
2. **空间问题**：标记清除后会产生大量不连续的内存碎片。.

<div align="center"> <img src="https://oss.javaguide.cn/github/javaguide/java/jvm/mark-and-sweep-garbage-collection-algorithm.png" width="75%"/></div>



#### 复制算法

为了解决标记-清除算法的效率和内存碎片问题，复制（Copying）收集算法出现了。它可以将内存分为大小相同的两块，每次使用其中的一块。当这一块的内存使用完后，就将还存活的对象复制到另一块去，然后再把使用的空间一次清理掉。这样就使每次的内存回收都是对内存区间的一半进行回收。

虽然改进了标记-清除算法，但依然存在下面这些问题：

- **可用内存变小**：可用内存缩小为原来的一半。
- **不适合老年代**：如果存活对象数量比较大，复制性能会变得很差。



<div align="center"> <img src="https://oss.javaguide.cn/github/javaguide/java/jvm/copying-garbage-collection-algorithm.png" width="75%"/></div>

#### 标记-整理算法

标记-整理（Mark-and-Compact）算法是根据老年代的特点提出的一种标记算法，标记过程仍然与“标记-清除”算法一样，但后续步骤不是直接对可回收对象回收，而是让所有存活的对象向一端移动，然后直接清理掉端边界以外的内存。

由于多了整理这一步，因此效率也不高，适合老年代这种垃圾回收频率不是很高的场景。



#### 分代收集算法

当前虚拟机的垃圾收集都采用分代收集算法，这种算法没有什么新的思想，只是根据对象存活周期的不同将内存分为几块。一般将 Java 堆分为新生代和老年代，这样我们就可以根据各个年代的特点选择合适的垃圾收集算法。

比如在新生代中，每次收集都会有大量对象死去，所以可以选择”复制“算法，只需要付出少量对象的复制成本就可以完成每次垃圾收集。而老年代的对象存活几率是比较高的，而且没有额外的空间对它进行分配担保，所以我们必须选择“标记-清除”或“标记-整理”算法进行垃圾收集。

### CMS垃圾回收器

**CMS（Concurrent Mark Sweep）** 是一款以获取**最短回收停顿时间**为目标的收集器，主要**作用于老年代**，基于**标记-清除（Mark-Sweep）**算法。

它的工作流程分为四个步骤：

1. **初始标记**：标记GC Roots能直接关联到的对象。**需要STW，但速度很快**。
2. **并发标记**：从GC Roots开始遍历整个对象图，标记所有存活对象。**耗时较长，但与用户线程并发执行，不暂停应用**。
3. **重新标记**：修正并发标记期间因用户程序继续运行而产生变动的对象标记。**需要STW，耗时比初始标记稍长**。
4. **并发清除**：清理删除标记阶段判断为已死亡的对象。**与用户线程并发执行**。



### G1垃圾回收器

G1 收集器的运作大致分为以下几个步骤：

- **初始标记**： 短暂停顿（Stop-The-World，STW），标记从 GC Roots 可直接引用的对象，即标记所有直接可达的活跃对象
- **并发标记**：与应用并发运行，标记所有可达对象。 这一阶段可能持续较长时间，取决于堆的大小和对象的数量。
- **最终标记**： 短暂停顿（STW），处理并发标记阶段结束后残留的少量未处理的引用变更。
- **筛选回收**：根据标记结果，选择回收价值高的区域，复制存活对象到新区域，回收旧区域内存。这一阶段包含一个或多个停顿（STW），具体取决于回收的复杂度。

**G1的四步走：先快照标记根对象（初始标记），然后慢慢画关系网（并发标记），接着修正关系变化（最终标记），最后挑垃圾最多的区域复制清理（筛选回收）。**

**G1最大的特色：分区思路（Region）**

你提到的“弱化分代概念”非常准确。这是G1与之前所有回收器最本质的区别。

- **传统回收器**：堆内存是**物理连续**的，新生代、老年代是两块独立的、边界固定的大区域。
- **G1**：把整个堆划分为几百到几千个大小相等的**独立小区域（Region）**。每个Region在逻辑上可以扮演Eden、Survivor或老年代的角色，但这种角色是**动态**的。

**这个设计的妙处**：

1. **灵活**：不需要为新生代和老年代预留固定的边界，内存利用率更高。
2. **可预测**：因为回收单位是Region（而不是整个代），G1可以每次挑选**垃圾最多**的几个Region优先回收（这就是Garbage First名字的由来），从而在**可控的停顿时间内回收最多的内存**。
3. **避免了Full GC的常见诱因**：传统回收器分配大对象时，如果老年代连续空间不足，会触发Full GC。G1中，大对象可以直接分配在专门的**Humongous Region**（巨型区域）中，不占用普通Region的连续空间。



| 对比维度     | **CMS 收集器**                                               | **G1 收集器**                                                |
| :----------- | :----------------------------------------------------------- | :----------------------------------------------------------- |
| **回收范围** | **老年代**。需配合新生代收集器（如 Serial、ParNew）使用。    | **整堆 (Young + Old)**。可独立管理整个堆，无需搭配其他收集器。 |
| **核心算法** | **标记-清除 (Mark-Sweep)**                                   | **整体标记-整理 (Mark-Compact)**，局部基于**复制 (Copying)** |
| **主要目标** | 尽可能**缩短应用暂停时间**（低延迟）。                       | 在**可预测的停顿时间**内，实现**高吞吐量**和低延迟。         |

### 什么情况下使用CMS，什么情况使用G1?

CMS适用场景：

- **低延迟需求**：适用于对停顿时间要求敏感的应用程序。
- **老生代收集**：主要针对老年代的垃圾回收。
- **碎片化管理**：容易出现内存碎片，可能需要定期进行Full GC来压缩内存空间。

G1适用场景：

- **大堆内存**：适用于需要管理大内存堆的场景，能够有效处理数GB以上的堆内存。
- **对内存碎片敏感**：G1通过紧凑整理来减少内存碎片，降低了碎片化对性能的影响。
- **比较平衡的性能**：G1在提供较低停顿时间的同时，也保持了相对较高的吞吐量。



### ZGC垃圾回收器

与 CMS、ParNew 和 G1 类似，ZGC 也采用标记-复制算法，不过 ZGC 对该算法做了重大改进。

ZGC 可以将暂停时间控制在几毫秒以内，且暂停时间不受堆内存大小的影响，出现 Stop The World 的情况会更少，但代价是牺牲了一些吞吐量。ZGC 最大支持 16TB 的堆内存。

ZGC 在 Java11 中引入，处于试验阶段。经过多个版本的迭代，不断的完善和修复问题，ZGC 在 Java15 已经可以正式使用了。

不过，默认的垃圾回收器依然是 G1。你可以通过下面的参数启用 ZGC：

```bash
java -XX:+UseZGC className
```

### minorGC、majorGC、fullGC的区别，什么场景触发full GC

在Java中，垃圾回收机制是自动管理内存的重要组成部分。根据其作用范围和触发条件的不同，可以将GC分为三种类型：Minor GC（也称为Young GC）、Major GC（有时也称为Old GC）、以及Full GC。以下是这三种GC的区别和触发场景：

#### Minor GC (Young GC)

- **作用范围**：只针对年轻代进行回收，包括Eden区和两个Survivor区（S0和S1）。
- **触发条件**：当Eden区空间不足时，JVM会触发一次Minor GC，将Eden区和一个Survivor区中的存活对象移动到另一个Survivor区或老年代（Old Generation）。
- **特点**：通常发生得非常频繁，因为年轻代中对象的生命周期较短，回收效率高，暂停时间相对较短。

#### Major GC

- **作用范围**：主要针对老年代进行回收，但不一定只回收老年代。
- **触发条件**：当老年代空间不足时，或者系统检测到年轻代对象晋升到老年代的速度过快，可能会触发Major GC。
- **特点**：相比Minor GC，Major GC发生的频率较低，但每次回收可能需要更长的时间，因为老年代中的对象存活率较高。

#### Full GC

- **作用范围**：对整个堆内存（包括年轻代、老年代以及永久代/元空间）进行回收。
- **触发条件**：
  - 直接调用`System.gc()`或`Runtime.getRuntime().gc()`方法时，虽然不能保证立即执行，但JVM会尝试执行Full GC。
  - Minor GC（新生代垃圾回收）时，如果存活的对象无法全部放入老年代，或者老年代空间不足以容纳存活的对象，则会触发Full GC，对整个堆内存进行回收。
  - 当永久代（Java 8之前的版本）或元空间（Java 8及以后的版本）空间不足时。
- **特点**：Full GC是最昂贵的操作，因为它需要停止所有的工作线程（Stop The World），遍历整个堆内存来查找和回收不再使用的对象，因此应尽量减少Full GC的触发



### 什么是 Heap Dump 文件？如何生成 Heap Dump 文件？

Heap Dump（堆转储文件）是 Java 虚拟机（JVM）在某个特定时间点，对整个 Java **堆内存**的快照。它是一个二进制文件，包含了快照时刻堆中所有对象的信息，例如：

- **对象实例**：每个对象的数据。
- **类信息**：对象的类名、父类、静态字段等。
- **引用关系**：对象之间复杂的引用链，即谁持有了谁。
- **线程信息**：堆栈信息，特别是与 GC Roots 相关的线程栈。

简单来说，Heap Dump 就是 Java 进程在某一刻的“内存 X 光片”，是诊断内存问题的最核心、最权威的依据。



#### 自动生成

在 JVM 启动参数中加入以下配置，这是生产环境排查 OOM 问题的首选方案。

```bash
# 当发生 OutOfMemoryError 时，自动生成 Heap Dump 文件
-XX:+HeapDumpOnOutOfMemoryError

# 指定 Heap Dump 文件的生成路径，例如：/home/app/dumps/
-XX:HeapDumpPath=<path-to-dump-dir>
```

#### 手动生成

当应用出现内存疑似异常（如内存持续升高、GC 频繁）但未崩溃时，可以手动生成快照进行分析。

1. **jmap** ：JDK 自带的命令行工具，专门用于生成堆快照。使用示例：`jmap -dump:format=b,file=heapdump.hprof <pid>`。在执行时会触发 STW ，导致 Java 进程短暂停顿，对生产环境有一定影响。在高版本 JDK 中已不推荐直接使用。
2. **jcmd** ：JDK 7 之后引入的多功能命令行工具，功能比 jmap 更强大一些，可用来替代 jmap，侵入性更小。使用示例：`jcmd <pid> GC.heap_dump /path/to/heapdump.hprof`。
3. **Arthas**：阿里巴巴开源的 Java 诊断神器，对应用无侵入，功能强大，可在不重启服务的情况下动态分析。使用示例：`heapdump /tmp/heapdump.hprof`。
4. **可视化工具**：如 JVisualVM、JProfiler、YourKit 等，都提供了图形化界面，点击按钮即可生成 Heap Dump 文件，并能直接进行分析，非常方便。

### 遇到 OutOfMemoryError 怎么排查解决？

我们可以通过 MAT、JVisualVM 等工具分析 Heap Dump 找到导致`OutOfMemoryError` 的原因。

以 MAT 为例，其提供的泄漏嫌疑（Leak Suspects）报告是 MAT 最强大的功能之一。它会基于启发式算法自动分析整个堆，直接指出最可疑的内存泄漏点，并给出详细的报告，包括问题组件、累积点（Accumulation Point）和引用链的图示。
