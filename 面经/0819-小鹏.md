## Answer

### A3：

记忆分层是怎么做的：

分层是物理隔离的：

短期(`working` ≤8 文件 / `episodic_notes` ≤12 条 / `file_summaries`)全在 `session.json` 里、靠容量 FIFO 和 SHA256 指纹失效自动遗忘;

长期在 `.pico/memory/` 的 markdown 文件树(MEMORY.md 索引 + 四个固定主题:约定/决策/依赖/偏好)、跨会话永久且不自动遗忘；两层之间只有一条晋升通道，须过"用户显式授权 → 结构化句式 → 反向否决(密钥/任务状态/噪音) → 同主语覆盖(supersede 并记血缘)"四道关，其中覆盖机制专治长期记忆的矛盾累积;而在消费端两层是统一的——正文都走 `relevant_memory` 的同一套四元组召回竞争 top-3，仪表盘只广播索引(笔记数量、主题名)；"分层"的实质就是每层有不同的遗忘策略。

我把它拆成四道关卡: 

**① 分层靠寿命**——偶发行为进会话级(带 FIFO 上限,自然遗忘);任务目标进任务级(随任务结束失效);稳定知识进长期层。**低层默认遗忘,所以'不重要'不需要判断。**

 **② 晋升靠显式授权**——只有用户说了'记住/保存'才考虑写入长期层,**默认不记**,避免噪音和隐私风险。

 **③ 内容靠结构化标记**——只接受'约定/决策/依赖/偏好'这四种声明式句式,既做筛选又完成归类,不需要额外的分类模型。 

**④ 反向否决**——密钥形状的、任务状态型的(`当前目标/下一步`)、以及工具输出噪音一律拒绝;任务状态最容易被误当成重要信息,但它属于 checkpoint 层,写进长期记忆下次就是错的。而且拒绝原因要落审计。 另外还有一条正交维度:**可重建性**决定压力下先牺牲谁——可重算的信息即使有用也优先丢弃。



**"为什么不用 LLM 判断重要性?"** 

→ 不确定、不可复现、每次多花一次调用,而且**误判会污染长期存储且难以发现**。规则法可解释、可审计、可测试。代价是召回率低(用户没按格式写就不记)，但**长期记忆宁可漏记,不可错记**——错的长期记忆会持续毒化后续每一轮。

**"用户没说'记住',但确实是重要偏好呢?"** → 承认这是这套设计的**已知取舍**(精确率优先于召回率)。渐进改法：先用规则法保底,再叠一层"候选+用户确认"的软提议(把 LLM 判断降级为建议而非直写),**始终保留人在回路**。





### A4：

Claude Code 的上下文压缩并非单一策略，而是一套**分层的防御体系**。它会根据上下文压力的严重程度，从低成本、规则化的处理，逐步升级到需要调用大模型的深度总结。

这套压缩机制的核心，按触发的先后顺序可以分为以下四个主要层次：

**第一层：MicroCompact（微压缩）—— 规则驱动的“第一道防线”**

这是最轻量、最优先触发的压缩策略，主要针对**结构化的工具输出**（如文件读取、Bash命令结果等）进行处理。它的特点是**不调用大模型**，完全通过规则来清理“上下文垃圾”，性价比极高。

*   **白名单机制**：系统只对`Read`、`Bash`、`Grep`、`Glob`等能产生大量标准输出的工具执行微压缩。
*   **时间与缓存感知**：会清除过时的旧工具输出，并智能避开可能影响Prompt Cache的部分，以最大化缓存命中率。
*   **静态估算**：对于图片等无法直接量化的内容，采用固定上限（如每张图最多2000 tokens）进行估算，避免复杂的计算开销。

**第二层：Session Memory Compact（会话记忆压缩）—— 复用已有的“智慧”**

如果微压缩效果不足，系统会进入这一层。它的核心是**复用之前交互中已经生成的高质量会话记忆**，直接用现成的摘要替换冗长的原始历史消息。

这同样是**不产生额外API调用**的轻量级操作，其触发也有门槛，比如只有在上下文Token数超过10,000且文本消息超过5条等条件满足时才会触发。

**第三层：Full LLM Compact（完全LLM压缩）—— 高精度的“终极手段”**

当前两层策略都无法有效控制上下文时，系统会亮出“重型武器”：**单独发起一次API调用，让Claude模型本身来生成一个结构化的全面摘要**。

*   **结构化模板**：压缩并非简单的“总结一下”，而是强制模型遵循一套严格的9段式模板，确保任务目标、关键技术概念、文件路径、待办事项等关键信息不被遗漏。
*   **隐式推理**：提示词会引导模型先在一个`<analysis>`块内进行逻辑推演，再将最终摘要输出在`<summary>`块中，以此提升摘要质量。系统最终会剥离分析过程，只保留纯净的摘要。
*   **防止工具调用**：提示词中会加入强约束，严厉禁止模型在压缩过程中调用任何工具，防止产生不可控的副作用。

**第四层：Auto-Compact（自动压缩触发）与恢复机制 —— 智能的“交通管制”**

一个完整的策略还需要一个智能的“交通管制中心”，来有序地协调上述手段的运作和应对突发情况。

*   **触发阈值**：系统会设定一个安全缓冲水位线（如预留13,000 tokens），当上下文窗口剩余空间低于这个阈值时，自动压缩就会被触发。
*   **熔断保护**：系统内置了熔断器。如果连续压缩失败达到一定次数（如3次），会自动停止该会话的压缩请求，防止徒劳消耗API额度。
*   **紧急降级（Context Collapse）**：当API因上下文过长返回错误（如413错误）时，系统会使用`Context Collapse`策略作为紧急恢复手段。它不修改原始消息，而是通过维护一个“压缩日志”来创建一个虚拟的压缩视图，从而快速释放上下文空间。
*   **持久化与重建**：压缩后的摘要和`compact_boundary`标记会被写入本地会话文件（JSONL）。当会话恢复时，系统会读取这些标记，从该点重建上下文，确保会话的连贯性。



### A6：

简单来说，MCP协议通过**传输层**来负责客户端与服务器之间的实际通信，目前有 `stdio` 和 `Streamable HTTP` 两种标准方式。

| 传输机制                 | 核心特点                                                     | 主要应用场景                                                 |
| :----------------------- | :----------------------------------------------------------- | :----------------------------------------------------------- |
| **Stdio 传输**           | 通过**标准输入/输出流**进行通信。性能最佳，无网络开销，**仅支持本地进程间通信**。 | 本地集成、命令行工具、与shell脚本协作等需要**最高性能**的本地场景。 |
| **Streamable HTTP 传输** | 基于**标准HTTP协议**，使用POST请求和（可选的）服务器发送事件（SSE）实现流式功能。**支持远程服务器通信**和标准HTTP认证（如OAuth）。 | 网络服务、需要远程访问或客户端与服务器解耦部署的场景。       |
