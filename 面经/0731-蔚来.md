## Q4：

### 第一：容量预分配（避免扩容风暴）

**核心原则**：HashMap的扩容机制（`resize()`）涉及新建数组和重新计算所有Key的索引（`rehash`），这是大数据场景下最耗时的操作，必须确保全程不触发扩容。

**计算公式**：

> **初始容量 = ( 预估数据量 / 负载因子 ) + 1**

然后对该数值向上取整为 **2的幂次方**（因为HashMap要求容量必须为2的幂，否则会自动修正）。

- 错误示范：预估100万数据，直接 `new HashMap<>(1_000_000)`。
  后果：默认负载因子0.75，实际扩容阈值仅为 `1,000,000 * 0.75 = 750,000`，写入到75万时就会触发扩容，之前的预分配失去意义。
- 正确做法：`int capacity = (int) (1_000_000 / 0.75f) + 1 = 1_333_334`，再取最近的2的幂（`2^21 = 2,097,152`），确保阈值远大于100万。

### 第二：谨慎调整负载因子（时间与空间的博弈）

- **保持默认 0.75**：这是官方经过数学验证的最优时空平衡点。**不建议**为了省内存调高至0.9或1.0，因为负载因子越高，哈希冲突越剧烈，链表/红黑树会变长，写入和查询的时间复杂度会从O(1)退化为O(log n)甚至O(n)，在大数据量下性能骤降。
- **唯一可调场景**：如果内存极其稀缺且对查询性能要求不高，可考虑设为0.8~0.85，但必须经过严格的压测验证。

### 第三：优化Key的哈希质量（减少内部碰撞）

大数据量下，即使容量设对，如果Key的`hashCode()`实现不佳（例如大量字符串拥有相同的前缀或后缀，导致低位特征不明显），仍会集中落入同一个桶。

- **措施1**：如果Key是自定义对象，务必重写高质量的`hashCode()`，利用`Objects.hash()`或引入随机因子打散低位。
- **措施2**：如果Key是String且长度较长，可考虑调用`String.hashCode()`后，再手动进行**高位扰动**（`hash ^= hash >>> 16`），进一步降低碰撞概率。

### 第四：选择合适的Map实现（突破原生限制）

原生`HashMap`的每个`Node`对象（约32字节）在大数据量下会造成巨大的内存开销，极易触发**Full GC**。

- **方案A（高性能库）**：引入 **FastUtil** 或 **Koloboke** 的`Object2ObjectOpenHashMap`。它们针对原始类型（int/long）做了无装箱优化，内存占用比JDK原生少30%~50%，且插入吞吐量更高。
- **方案B（只存不查）**：如果业务仅需判断Key是否存在（无需存储Value），使用 **Guava的BloomFilter**（布隆过滤器），内存占用可降低至几MB级别。

### 第五：终极兜底与分治策略（防止OOM）

**重要前提**：所有数据必须存储在JVM堆内吗？如果预估数据量超过堆内存的40%，强行Put会导致频繁Full GC甚至OOM。

- **水平分片（Sharding）**：根据Key的哈希值取模，将数据分散到多个独立的`HashMap`实例中，或者直接使用 **ConcurrentHashMap** 的`compute`方法配合分段处理，但从物理上更推荐借助外部存储。
- **降级至外部存储**：改用 **Redis Cluster**（内存型）或 **RocksDB**（LSM树，磁盘型）承接数据，利用其自身的批量写入（`Batch`）和异步刷盘机制，彻底解决JVM内存瓶颈。

#### 补充：写入时的编码细节

- 优先使用 **`putAll()`** 方法批量写入（内部有批量扩容优化），避免在循环中逐条`put`。
- 如果使用JDK 8+，可结合 **`computeIfAbsent()`** 处理复杂Value的懒加载，避免重复创建对象增加GC压力。

**总结**：面对大数据量Put，我追求的核心目标是 **“零扩容 + 低碰撞 + 省内存”**，按优先级依次是：**精准计算容量 → 选用高性能库 → 若单机扛不住则水平分片或落盘**。如果面试官您感兴趣，我可以针对FastUtil的性能对比或分片路由算法再做展开。





## Q5：

### JDK17新特性

#### 1. 密封类 (Sealed Classes) - JEP 409 

**正式转正**：密封类在JDK 15和16中作为预览功能，在17中正式确定下来。

**核心作用**：允许类或接口对其可以扩展或实现的子类型进行**受控的、有限的继承**。这能更精确地建模领域模型，增强代码安全性。

```java
// 使用 sealed 关键字声明，permits 列出允许的子类
public sealed class Shape permits Circle, Rectangle, Triangle {
    // ...
}

// 子类必须是 final、sealed 或 non-sealed
final class Circle extends Shape { /* ... */ }
non-sealed class Rectangle extends Shape { /* ... */ }
```



#### 2. switch 模式匹配 (预览) - JEP 406 

**预览特性**：在JDK 17中作为**预览语言特性**提供，需要启用预览功能才能使用。

**核心改进**：极大地增强了`switch`的能力。现在，`switch`的`case`标签可以使用**模式（Patterns）**，而不仅仅是常量。

**主要优势**：

- **支持更多类型**：`switch`可以直接处理任何类型的对象。
- **自动解构**：当匹配成功时，可以直接从模式中提取变量，免去了在`case`块里手动进行`instanceof`检查和强制类型转换的麻烦。

```java
// 传统的 if-else 链
String formatter(Object o) {
    if (o instanceof Integer i) { return String.format("int %d", i); }
    else if (o instanceof Long l) { return String.format("long %d", l); }
    // ...
}

// 使用 switch 模式匹配 (预览)
String formatterPatternSwitch(Object o) {
    return switch (o) {
        case Integer i -> String.format("int %d", i);
        case Long l    -> String.format("long %d", l);
        case Double d  -> String.format("double %f", d);
        case String s  -> String.format("String %s", s);
        default        -> o.toString();
    };
}
```



### JDK21新特性

#### 1. 虚拟线程

- **虚拟线程 (Virtual Threads) - JEP 444 (正式版)**：这是 JDK 21 最核心、最受期待的特性。它是一种**轻量级线程**，创建和销毁的成本极低。传统的平台线程是“重型卡车”，而虚拟线程是“海量共享单车”，一个平台线程可以托管成千上万个虚拟线程。
  - **应用场景**：特别适合**I/O密集型任务**（如大量的数据库查询、远程服务调用）。用虚拟线程处理百万级并发不再是天方夜谭，而内存消耗却非常小，彻底解决了传统线程池“撑爆”的难题。
  - **简单用法**：通过 `Thread.ofVirtual().start(...)` 即可轻松创建。
- **结构化并发 (Structured Concurrency) - JEP 453 (预览版)**：这是一种全新的并发编程思想，将多个线程任务的生命周期绑定在一个代码块内（类似 `try-with-resources`）。它能让线程管理变得像写同步代码一样清晰，**自动处理线程的取消和异常传播**，避免了线程泄漏和复杂的 `Future.get()` 异常处理。

#### 2. 代码优化

* 序列集合 (Sequenced Collections) - JEP 431 (正式版)：为 `List`、`Set`、`Map` 等有序集合统一了操作首尾元素的方法，终于不用再写 `list.get(list.size()-1)` 这样的代码了
* 未命名模式和变量 - JEP 443 (预览版)：当不需要使用某个变量时，可以用下划线 `_` 替代，让代码意图更清晰，减少无用的变量名
