## Answer

### A2-如何处理哈希冲突

**链表阶段（桶中节点数 ≤ 7）**

- 当多个key的`hashCode`对数组长度取模后落在同一个桶时，采用**尾插法**插入。
- 插入顺序是**按冲突发生的时间先后**：先冲突的先在链表头部附近，新来的追加到尾部。
- 插入前会遍历链表，如果发现某个节点的`hash`相等且`equals`为true，则直接覆盖旧值，不插入新节点。



**红黑树阶段的比较逻辑（重点，含未实现Comparable）**

> **树化后（桶中节点数 ≥ 8）**，插入位置由**一套优先级明确的比较链**决定，**不是按时间顺序**：

| 比较层级              | 条件                                     | 操作                                                         |
| :-------------------- | :--------------------------------------- | :----------------------------------------------------------- |
| **第1层**             | 先比`hashCode`                           | 直接按int值大小比较，大的放右子树，小的放左子树。            |
| **第2层**             | `hashCode`相同，且key实现了`Comparable`  | 调用`compareTo()`方法决定左右。                              |
| **第3层**             | `hashCode`相同，但**未实现`Comparable`** | 使用`System.identityHashCode()`——这个方法返回基于**对象内存地址**的哈希值（与`hashCode()`不同，不会被重写覆盖），用它来比较大小。 |
| **第4层（终极兜底）** | 身份哈希值也相同（极端情况）             | 调用`tieBreakOrder()`方法：先比较两个对象的**类名**（`getClass().getName()`），若类名还相同，再用`System.identityHashCode`比一次。**保证任何两个不同对象都能分出确定的大小顺序。** |



**未实现Comparable”的专项回答**

> **如果key没有实现`Comparable`接口，HashMap的处理机制如下：**

1. **不会报错，也不会退化到链表**。红黑树依然可以正常构建和操作。
2. **比较逻辑自动降级**：
   - 当`hashCode`相同时，HashMap**不会**因为无法调用`compareTo()`而卡住。
   - 它会转而使用 `System.identityHashCode(key)` 来获取对象的内存地址哈希值。
   - 这个值在对象的整个生命周期中保持不变，且绝大多数情况下不同的对象拥有不同的身份哈希值，足以作为排序依据。
3. **极端情况下的兜底保证**：
   - 如果两个对象的`System.identityHashCode`碰巧也相同（虽然概率极低，但JVM规范允许），系统会通过`tieBreakOrder`方法比较类名。
   - 如果类名也相同（同一个类的两个不同实例），再用身份哈希比一次，**确保绝对不会出现无法比较的情况**。
4. **性能影响**：
   - 未实现`Comparable`时，比较逻辑从直接的`compareTo()`调用变成了`System.identityHashCode()`计算和可能的类名字符串比较，**性能会略有下降**，但这是为了保证功能完整性的必要代价。

**总结**

链表阶段的插入顺序是**尾插法的时间顺序**；红黑树阶段的插入顺序由**强制的排序规则**决定，与时间无关。即使key未实现`Comparable`，HashMap也能通过`System.identityHashCode`和`tieBreakOrder`兜底机制正常运作，保证红黑树的有序性和插入的正确性。



### A3-ConcurrentHashMap

**区分场景**

**1.读操作**

- 数组`table`和节点的`val`、`next`都用`volatile`修饰，保证**可见性**。
- 读操作完全无锁，多个线程可以同时读取，性能最高。
- 即使有线程正在写入或扩容，`volatile`能保证读线程看到最新状态（或通过`ForwardingNode`转发到新数组）。

**2.写操作（put）—— CAS + synchronized 组合**

| 情况                                   | 处理方式                                   | 线程安全手段                 |
| :------------------------------------- | :----------------------------------------- | :--------------------------- |
| **桶为空（首次插入）**                 | CAS尝试将新节点设置到桶头                  | **CAS**                      |
| **桶不为空（链表/树）**                | 遍历找到插入位置或覆盖旧值                 | **synchronized**锁住桶头节点 |
| **正在扩容（头节点为ForwardingNode）** | 当前线程**帮助扩容**（transfer），然后重试 | CAS领取任务 + synchronized   |



**并发写入空桶时的CAS工作流程**

假设有两个线程T1和T2同时向同一个空桶插入数据：

| 时间 | 线程T1                                                   | 线程T2                                                       | 内存中桶的状态                  |
| :--- | :------------------------------------------------------- | :----------------------------------------------------------- | :------------------------------ |
| t1   | 执行`casTabAt(tab, i, null, newNode1)`                   | 尚未执行                                                     | `null`                          |
| t2   | CPU执行`cmpxchg`指令，比较内存值为`null`，**期望值匹配** | —                                                            | `null` → `newNode1`（原子写入） |
| t3   | T1 CAS成功，返回true，插入完成                           | 执行`casTabAt(tab, i, null, newNode2)`                       | `newNode1`                      |
| t4   | —                                                        | CPU执行`cmpxchg`，比较内存值为`newNode1`，期望值是`null`，**不匹配** | `newNode1`                      |
| t5   | —                                                        | T2 CAS失败，返回false                                        | `newNode1`                      |
| t6   | —                                                        | T2进入**自旋**，重新读取桶状态，发现不为空，改用`synchronized`方式插入 | `newNode1`                      |

**关键点：**

- CAS失败的线程**不会阻塞**，而是立即返回失败，由调用方决定重试（自旋）还是改变策略。
- 这就避免了传统锁的**上下文切换开销**，在低冲突场景下性能极高。



### A4-QUIC

**连接建立速度、队头阻塞、连接迁移、拥塞控制、加密一体化**

QUIC = UDP + 自实现的可靠传输 + TLS 1.3内置加密，通过一次握手建立安全连接、流级独立消除队头阻塞、Connection ID支持连接迁移、用户态拥塞控制快速演进、强制加密默认安全，全面解决了TCP+TLS在HTTP传输中的性能痛点。



### A5-QUIC网络切换

**核心答案：Connection ID（连接标识符）**

一、核心原理

TCP通过**四元组**（源IP、源端口、目标IP、目标端口）标识连接，网络切换时四元组改变，连接立即中断。

QUIC在报文头部引入**Connection ID**，这是一个64位的连接标识符，**独立于IP和端口**。即使客户端的IP和端口发生变化，只要Connection ID不变，服务器就能识别出这是同一个连接。

二、工作流程

| 步骤          | 说明                                                    |
| :------------ | :------------------------------------------------------ |
| 1. 建立连接   | 首次握手时，客户端和服务器协商出Connection ID           |
| 2. 网络切换   | WiFi切到5G，客户端IP从192.168.1.10变为10.0.0.20         |
| 3. 继续传输   | 客户端用新IP发送报文，但仍携带原来的Connection ID       |
| 4. 服务端识别 | 服务器收到后通过Connection ID找到对应连接，继续传输数据 |
| 5. 新路径验证 | 双方通过加密校验确认对端身份，防止中间人劫持            |

三、为什么TCP做不到？

|            | TCP                          | QUIC                                     |
| :--------- | :--------------------------- | :--------------------------------------- |
| 连接标识   | IP + Port四元组              | Connection ID                            |
| 网络切换后 | 四元组变了→认为是新连接→断开 | 四元组变了，但Connection ID没变→连接继续 |

四、总结

> **QUIC通过Connection ID将连接与网络层（IP/端口）解耦，网络切换时连接标识不变，从而实现连接的无缝迁移，上层HTTP请求完全感知不到底层网络变化。**
