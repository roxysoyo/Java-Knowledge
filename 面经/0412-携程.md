### 线程池如何配置？

#### 第 1 层｜任务级线程池

`evaluationSimulationExecutor`

| 参数                               | 取值                              | 动机                                                         |
| :--------------------------------- | :-------------------------------- | :----------------------------------------------------------- |
| `corePoolSize`                     | `cores - 1`（≥1）                 | CPU 密集任务，N+1 经验值要扣掉给 Tomcat / GC 留余量的那一个核 |
| `maxPoolSize`                      | = core                            | 故意锁死无弹性。CPU 密集任务多开线程只增加上下文切换；让池稳态行为可预测 |
| `queueCapacity`                    | 128，有界                         | 无界 = OOM 风险 + 永远触发不了拒绝策略，是 `Executors.newFixedThreadPool` 经典坑 |
| `RejectedExecutionHandler`         | 计数 `CallerRunsPolicy`（自定义） | 不丢任务（蒙特卡洛少一次 = 均值偏差）；自定义版本额外暴露过载计数指标 |
| `WaitForTasksToCompleteOnShutdown` | `true` + 60s                      | 优雅停机，但 60s 在大批量下不够（仍是已知技术债，需配合 `runSimulation` 加中断检查） |
| `ThreadNamePrefix`                 | `eval-sim-`                       | `jstack` / Arthas 排查时一眼定位                             |
| `keepAliveTime`                    | 未配（无意义）                    | `core == max` 且 `allowCoreThreadTimeOut=false`，永远不触发  |

------

#### 第 2 层｜请求级闸门

`simulationGate`

```java
this.simulationGate = new Semaphore(maxConcurrentRequests, true);  // 默认 2，公平模式
// SimulateServiceImpl:54-70
```

| 参数             | 取值               | 动机                                                         |
| :--------------- | :----------------- | :----------------------------------------------------------- |
| `permits`        | 2（可配）          | 同时最多 2 个仿真请求在跑。比 1 多一点是为了不浪费第二台机器的并发能力，又不至于让多个请求挤进来打爆队列 |
| `fair`           | `true`             | 公平 FIFO，避免高频小请求把锁一直抢走、慢请求长期饿死。代价是吞吐略低，但仿真接口不是高 QPS 场景，公平更重要 |
| `acquireTimeout` | 默认 0（立刻 429） | 拿不到直接拒，让用户自己重试，不让请求阻塞 Tomcat 线程。可配置成"等 N 毫秒"，看业务偏好 |

`withGate(...)` 在 `try` / `finally` 里 `acquire` / `release`，保证异常路径也会释放 permit——这一点比线程池的拒绝策略更安全，因为 `Semaphore` 是显式控制的。

#### 第 3 层｜线程池指标暴露

自动暴露的 Micrometer 指标

| Metric                                   | 含义                           | 告警阈值参考                  |
| :--------------------------------------- | :----------------------------- | :---------------------------- |
| `eval-sim.executor.active`               | 活跃线程数                     | 持续 ≈ `cores-1` 说明长期打满 |
| `eval-sim.executor.queued`               | 队列长度                       | > 96 (75%) 告警，> 120 紧急   |
| `eval-sim.executor.completed`            | 累计完成任务数                 | 求导得到 QPS                  |
| `eval-sim.executor.pool.size`            | 当前线程数                     | 应稳定 = `cores-1`            |
| `eval-sim.caller_runs`（自定义 Counter） | 过载真信号——被调用方代跑的次数 | **任意非零都要告警**          |

#### 第 4 层｜可观测的 `CallerRunsPolicy`

最后一条是关键。原生 `CallerRunsPolicy` 不会增加 `ThreadPoolExecutor` 的 `rejected` 计数器，导致"线程池满 + 调用方在替它跑任务"这种危险状态完全不可观测。自定义实现：

```java
return new ThreadPoolExecutor.CallerRunsPolicy() {
    @Override
    public void rejectedExecution(Runnable r, ThreadPoolExecutor e) {
        counter.increment();           // ← 关键：暴露过载计数指标
        super.rejectedExecution(r, e);
    }
};
```



### 索引最左匹配原则是什么？在项目中是如何体现的？

#### 第 1 层｜问题本质拆解

复合索引 `idx(a, b, c)` 在 B+ 树里是按 `(a, b, c)` 的字典序排列的。当你查询时：

| 查询条件                          | 是否走 idx          | 原因                                                         |
| --------------------------------- | ------------------- | ------------------------------------------------------------ |
| `where a = ?`                     | ✅                   | 命中前缀 a                                                   |
| `where a = ? and b = ?`           | ✅                   | 命中前缀 (a,b)                                               |
| `where a = ? and b = ? and c = ?` | ✅ 完全命中          | 命中完整 (a,b,c)                                             |
| `where b = ?`                     | ❌                   | 跳过 a，索引项排序对 b 没意义                                |
| `where a = ? and c = ?`           | ⚠️ 部分命中          | 只用 a 部分，c 退化为扫描后过滤（MySQL 5.6+ 有 ICP 优化但不改变"c 没用上索引定位"的事实） |
| `where a > ? and b = ?`           | ⚠️ a 走索引但 b 不走 | 范围列后的等值列断链                                         |
| `where a = ? order by b`          | ✅ + 免排序          | 利用索引天然有序，省 filesort                                |

**底层原因**：B+ 树叶子节点是按 `(a, b, c)` 复合 key 排序的。给定 a 值，能定位到 a 的范围；在 a 范围内，b 是有序的，能继续二分。但**没有 a 的话，b 在整个表里是乱的**——必须全表/全索引扫描。

------

**推荐索引**：

```sql
-- DM8 / Oracle 风格
CREATE INDEX idx_indicator_data_scn_net_time_ind
    ON indicator_data (scenario_id, net_name, net_time, indicator_id);
```

**列顺序的工程理由**（这是面试官最爱深挖的）：

| 列             | 位置    | 理由                                                         |
| -------------- | ------- | ------------------------------------------------------------ |
| `scenario_id`  | 第 1 列 | **基数高 + 必填 + 所有查询都有**。一个场景下数据量大，先做粗筛分桶 |
| `net_name`     | 第 2 列 | 基数中等，按方案名筛选                                       |
| `net_time`     | 第 3 列 | 基数高（每次评估时间点不同），进一步缩小                     |
| `indicator_id` | 第 4 列 | 查询点 A 用 `IN`，覆盖在最右边，A 能命中 4 列；B 命中前 3 列 |

**为什么不是 `indicator_id` 在前**？基数高的列在前是个**经验法则不是铁律**。正确的判断标准是：**所有查询都会带哪个列？把"必出现"的放前面**。这里 `scenario_id` 是所有查询的必带条件，必须 first。

> 这一条解释能直接干掉 80% 的面试候选人——他们只会背"基数高的在前"。

### 平级建表（一张大宽表）是否违反范式？什么场景下可以接受？

#### 第 1 层｜问题本质拆解

面试官真正在考的：

1. 你**懂不懂范式存在的目的**（不是为了"优雅"，是为了消除三种异常）
2. 你**能不能识别工程里"该反范式"和"反错了"的边界**
3. 你**能不能用一致性的成本来论证什么场景下反范式合理**

简短结论先给出：

> **"全放一张表"绝大多数情况下违反范式（至少违反 3NF，常常连 1NF 也违反）。** 但**违反范式 ≠ 错**。在三类场景下反而是正解：
>
> 1. **读多写少 + 写时即终态**（评估结果、日志、事件）
> 2. **维度退化型分析表**（数据仓库的事实表）
> 3. **跨表 JOIN 已成瓶颈、一致性可松弛**（用一致性换性能）
>
> 反范式的代价不是"丑"，是**写入时一致性维护责任从 DB 转移到应用层**——这是真正的 trade-off。

------

#### 第 2 层｜范式真正想解决什么

把课本概念翻译成"它防什么":

| 范式     | 一句话定义           | 实际防的是什么异常                                           |
| -------- | -------------------- | ------------------------------------------------------------ |
| **1NF**  | 列值原子，不可再分   | 字符串拼接型存储（"A,B,C"）导致**无法用 SQL 直接查询某项**   |
| **2NF**  | 非主属性完全依赖主键 | 复合主键下，部分字段只依赖部分主键 → **重复存储 + 部分更新异常** |
| **3NF**  | 不存在传递依赖       | 字段 A → B → C → **C 改了要联动改所有冗余存储的地方**        |
| **BCNF** | 任何决定方都是候选键 | 比 3NF 严，常被实务忽略                                      |

**核心动机**：范式的存在是为了消除**"同一事实存储在多处"**导致的三种异常：

- **更新异常**：改 A 表忘了改 B 表 → 数据不一致
- **插入异常**：要插一条事实，但缺少某些字段无法插入
- **删除异常**：删一条事实顺带丢了不该丢的维度信息

一张大宽表的所有问题，本质都能归结到这三个里某一个。**反过来说：如果你的场景里这三个异常不会发生，违反范式就没代价**——这是判断"能不能反范式"的金标准。

------

#### 第 3 层｜KillEvaluation 里的范式实例

实例 1：`IndicatorData.equipments` — 已经违反 1NF

[IndicatorDataServiceImpl:365-369](vscode-webview://1i4csngisab2k9m17phsr4nos9p1vjj8tb6i698esio1f1hk59as/KillEvaluation/src/main/java/com/example/killevaluation/service/impl/IndicatorDataServiceImpl.java#L365-L369)：

```java
joinedEquipNames = relatedEquips.stream()
    .map(EquipData::getEquipmentName)
    .distinct()
    .collect(Collectors.joining("，"));
```

`equipments` 字段存的是 `"雷达，火炮，预警机"` 这种逗号拼接字符串——**典型的 1NF 违反**。

**这样做的代价**：

- ❌ 想查"用了雷达的所有方案" → 只能 `LIKE '%雷达%'`，全表扫
- ❌ 想统计每种装备出现次数 → SQL 干不了，得拉到应用层 split
- ❌ "雷达" 改名 "RadarV2" 时，要 UPDATE 所有包含它的行的字符串

**为什么 KillEvaluation 还这么做**：

- 这个字段是**给前端展示用的快照**，不参与查询
- 业务上不需要"反查"，只需要"前端看一眼这条指标关联了哪些装备"
- 同时还冗余存了 `preprocess`（计算方法），属于**展示态快照**

**判断**：**可接受的违反 1NF**——因为它本质上不是"关系数据"，而是"展示文案"。**关键证据**：这个字段在 SQL 查询里从来没作为过滤条件出现。

**何时不可接受**：如果哪天产品提"我要看用了雷达的所有指标"，这条字段立刻变债务，必须拆出独立的关联表 `indicator_data_equipment(indicator_data_id, equipment_id)`。

实例 2：`IndicatorData.preprocess` — 违反 3NF（传递依赖）

`preprocess`（"直线正相关型" / "直线负相关型"）**已经存在 `IndicatorStructure` 表里**了，理论上 `IndicatorData` 通过 `indicator_id → IndicatorStructure.preprocess` 就能拿到——这是经典的**传递依赖**，违反 3NF。

但 [IndicatorDataServiceImpl:153-160](vscode-webview://1i4csngisab2k9m17phsr4nos9p1vjj8tb6i698esio1f1hk59as/KillEvaluation/src/main/java/com/example/killevaluation/service/impl/IndicatorDataServiceImpl.java#L153-L160) 显式做了**强制同步**：

```java
boolean preprocessChanged = StrUtil.isNotBlank(preprocess) 
    && !Objects.equals(existing.getPreprocess(), preprocess);
if (... || preprocessChanged) {
    existing.setPreprocess(preprocess);  // 把指标定义的 preprocess 拷一份到 data 里
    ...
}
```

**这是一处有意识的反范式**。动机推测：

- `IndicatorStructure.preprocess` 是**指标的配置**，可能被产品/管理员后台修改
- `IndicatorData` 是**那一次评估时的数据快照**，需要记录"当时是按什么规则归一化的"
- 如果之后管理员把指标改成"直线负相关"，**历史评估数据的归一化结果不应该跟着变**——必须保留当时的语义

**判断**：**正确的反范式**——这是**时间点快照 vs 配置可变**的经典场景。一致性的责任由应用层显式承担（"写入时拷贝"），不再依赖 JOIN。

**面试加分点**：能识别这是"快照型反范式"而不是"懒得 JOIN" ——前者是设计，后者是技术债。

实例 3：`IndicatorFormula.paramDescriptionJson` — JSON 字段

[IndicatorFormula](vscode-webview://1i4csngisab2k9m17phsr4nos9p1vjj8tb6i698esio1f1hk59as/KillEvaluation/src/main/java/com/example/killevaluation/entity/po/IndicatorFormula.java) 表里把公式参数描述存成 JSON 字符串。**JSON 字段算不算违反 1NF？**

教科书答案：**算**，因为 JSON 内部不原子。 工程答案：**取决于你怎么用它**：

- 只整体读取、不做 JSON 内部查询 → **不违反**（等同于 BLOB / TEXT，DB 不关心内部结构）
- 在 SQL 里 `WHERE json_extract(...) = ?` 做过滤 → **违反**，应该拆表

KillEvaluation 里这个字段在 [SpelFormulaExecutor](vscode-webview://1i4csngisab2k9m17phsr4nos9p1vjj8tb6i698esio1f1hk59as/KillEvaluation/src/main/java/com/example/killevaluation/formula/SpelFormulaExecutor.java) 中是**整体读出来反序列化**，不做 SQL 查询——属于**可接受的"半结构化字段"**。

**面试要点**：现代 RDBMS（PostgreSQL JSONB / MySQL 8 / DM8）都支持 JSON 类型 + GIN 索引，1NF 的边界已经被工程实践冲淡了——但底线是"是否需要 SQL 引擎理解它的内部"。

实例 4：Redis 里的"大树"是反范式到极致

[AbstractEvaluationTemplate](vscode-webview://1i4csngisab2k9m17phsr4nos9p1vjj8tb6i698esio1f1hk59as/KillEvaluation/src/main/java/com/example/killevaluation/evaluation/AbstractEvaluationTemplate.java) 把整棵评估树（含所有方案的所有指标分数）序列化成 JSON 写进 Redis。如果这是 DB 表，那简直是**违反所有范式的范本**：

- 一行包含多个方案的多个指标 → 1NF 违反到爆
- 父节点冗余存储所有子节点 → 任意范式都违反

**但这是合理的**：

- Redis 不是事务型存储，**不需要范式保护**
- 写入路径单一（评估算完一次性写），没有更新异常
- 读取路径就是"按方案 ID 拿整棵树"，**结构匹配查询模式**
- 失效靠 TTL + 重新评估时覆写

**这是范式讨论里很重要的一个分水岭**：**OLAP/缓存/物化视图** 这一侧的存储，范式失去意义。

实例 5：如果把 KillEvaluation 全摊平会怎样

假设有人提议"全放一张表"，schema 像这样：

```
mega_table(
    scenario_id, net_name, net_time, indicator_id,
    -- 指标定义（来自 IndicatorStructure）
    indicator_name, parent_id, level_depth, weight_ahp, weight_topsis,
    min_val, max_val, preprocess, is_visible, is_deleted,
    -- 数据值
    raw_value, normalized_value, final_score, is_manual,
    -- 公式
    formula_expr, param_json,
    -- 装备
    equipments_str
)
```

会出现什么问题？

| 问题                 | 具体表现                                                     |
| -------------------- | ------------------------------------------------------------ |
| **更新异常**         | 改一个指标名称要 UPDATE 所有方案下所有时间点该指标的行（可能上千行） |
| **插入异常**         | 想加一个新指标定义（还没评估过），没数据可填，要么插一条假数据要么留 null |
| **删除异常**         | 想删除某次评估的数据（一个方案），顺便会丢失"这个指标的定义"——因为定义只存在于行里 |
| **AHP 矩阵无处安放** | N 个子指标有 N×N 个相对重要度，**无法塞进同一张表的同一行**  |
| **空间膨胀**         | 指标定义重复 N×M×K 次（方案数 × 时间点 × 评估次数）          |

**结论**：KillEvaluation 这种"指标树 + 多方案 + 矩阵"的业务，**核心实体模型本身就不适合单表**，强行摊平会被业务复杂度反噬。

------

#### 第 4 层｜什么场景下"反范式 / 大宽表"可以接受

这是真正的核心。我列出**5 个真实工程场景**，每个都说明**为什么这里反范式不会触发三种异常**：

场景 1：数据仓库的事实表（OLAP）

```sql
fact_sales(date_id, store_id, sku_id, category_name, brand, region, ..., qty, amount)
```

- `category_name` / `brand` 本来应该在 dim 表里
- 但事实表是**写入时一次性入库 + 之后只读**
- 不会有"改 brand 名称"的运营动作（即使有也是新建一条）
- 读取时省 JOIN，扫描快几倍

**为什么没事**：**写后不改 + 维度退化**。

场景 2：日志 / 事件流

```
event_log(event_id, user_id, user_name, user_role, action, payload, timestamp)
```

- `user_name` 显然违反 3NF（依赖 user_id）
- 但日志是**append-only**，永远不会更新
- 即使用户改名，历史日志保留"当时叫什么"反而是审计需求

**为什么没事**：**append-only + 时间快照本身是业务语义**。

场景 3：评估结果 / 报表快照

**这就是 KillEvaluation 的评估树 Redis 缓存**——评估算完之后是**只读结果**，写一次读 N 次。

类似的工程例子：

- 报表每天凌晨生成一份快照表
- 推荐系统的离线结果落表

**为什么没事**：**写时一次性、读时不 JOIN、失效靠重建而不是更新**。

------

#### 第 5 层｜什么场景**绝对不能**反范式

| 场景                                     | 原因                       |
| ---------------------------------------- | -------------------------- |
| 高频更新的业务实体（订单、用户、库存）   | 更新异常风险大             |
| 多人协作编辑的实体                       | 并发更新冲突放大           |
| 强一致性要求的财务系统                   | 任何冗余都可能导致对账失败 |
| 业务模型本身就是图/树结构（如 AHP 矩阵） | 关系基数本身无法摊平       |

------

#### 第 6 层｜面试官会怎么深挖

攻击点 1：你说"反范式用一致性换性能"，具体怎么换？

**正确答案**：

- **写时双写**：应用层在更新源表的同时更新冗余表（事务里或者 outbox 模式）
- **异步同步**：CDC（Canal / Debezium）订阅源表 binlog 异步同步冗余
- **定时全量重建**：每天凌晨重算冗余表（适合容忍 T+1 延迟）
- **读时合并**：源表 + 冗余表都读，应用层取新的（最不优雅）

KillEvaluation 用的是**写时显式拷贝**（[IndicatorDataServiceImpl:155-161](vscode-webview://1i4csngisab2k9m17phsr4nos9p1vjj8tb6i698esio1f1hk59as/KillEvaluation/src/main/java/com/example/killevaluation/service/impl/IndicatorDataServiceImpl.java#L155-L161)）。

攻击点 2：为什么很多大厂业务系统反而用范式？

**正确答案**：

- 大厂业务复杂 + 多团队协作 → **范式提供"单一真相源"，避免数据漂移**
- 性能问题用**缓存 + 读写分离 + 分库分表**解决，**不用反范式**
- 反范式是"性能优化的最后手段"，不是首选
- KillEvaluation 这种内部工具系统，写少读少，更没必要反范式

攻击点 3：你怎么看"宽表 = 上来就摊平所有未来可能用到的字段"这种设计？

**正确答案**（这是接近"实战经验" 的问题）：

- **预先冗余 = 预先承担一致性维护成本**
- 不知道未来会不会用的字段，宁可不冗余
- 真有性能问题再加冗余，而不是预防式宽表
- **真实事故**：预先冗余了 20 个字段，结果一致性维护逻辑写错了 5 个，业务跑了半年才发现，数据已经污染

------

#### 总结

> **范式的本质是"消除同一事实的多处存储"，反范式的本质是"用应用层一致性换查询性能"**。 在 KillEvaluation 里：`IndicatorData.preprocess` 的冗余存储是**正确的快照型反范式**（业务语义需要），`IndicatorData.equipments` 的字符串拼接是**可接受的展示型反 1NF**（不参与查询），Redis 评估树是**极致的反范式但合理**（写后只读、靠 TTL 失效）。 真正不能接受的是 **"全摊平到一张表"**——KillEvaluation 的指标树 × 方案矩阵 × 时间点结构本身就不是一张表能承载的关系基数。





### 如何分析一条慢 SQL？

#### 第 1 层｜问题本质拆解

这道题实际考三件事：

1. 有没有一套定位慢 SQL 的方法论（不是只会 `EXPLAIN` 一把梭）
2. 对 EXPLAIN 输出列的语义到不到位（不是背 type 表）
3. 能不能根据 type 反推怎么优化（这才是真正的工程能力）

最值钱的是第三步：看到 `ALL` 怎么办，看到 `range` 是不是就 OK 了，`range` 扫了 100 万行算快吗？

------

#### 第 2 层｜分析一条慢 SQL 的方法论

Step 1：怎么发现慢 SQL（前置）

| 来源       | 工具                                                         |
| ---------- | ------------------------------------------------------------ |
| 慢查询日志 | MySQL: `slow_query_log` + `long_query_time`；DM8: `INI` 配置 `SVR_LOG=1` + 慢 SQL 阈值 |
| 应用监控   | Druid 监控页（KillEvaluation 用的就是 Druid）/ APM / Pinpoint |
| 业务上报   | 用户/前端反馈某接口慢，反查关联 SQL                          |

KillEvaluation 已经用了 Druid（[根 POM:51-53](vscode-webview://1i4csngisab2k9m17phsr4nos9p1vjj8tb6i698esio1f1hk59as/pom.xml#L51-L53)），SQL 监控应该在 Druid 的 `/druid/sql.html` 页面能直接看到 TOP N 慢 SQL，**但当前代码里没有看到对 Druid 监控的配置 / 权限保护**，这是一个可补的工程点。

Step 2：定位瓶颈 — 不是只有 EXPLAIN

```
慢 SQL 出现
  │
  ▼
┌─ EXPLAIN ──────────── 看 type / rows / Extra
│
├─ EXPLAIN FORMAT=JSON ── 看 cost、filter、used_index 详情
│
├─ EXPLAIN ANALYZE ──── (MySQL 8.0+) 真实执行 + 实际行数
│
├─ SHOW PROFILE ────── (即将废弃) 看每个阶段耗时
│
├─ OPTIMIZER_TRACE ──── 优化器选索引的过程
│
├─ performance_schema ── 锁等待、IO 等待
│
└─ 慢 SQL 全文 ───────── 看是否能改写
```

**90% 的慢 SQL 在 EXPLAIN 一步就能定性**，剩下的 10% 才需要 ANALYZE / trace。

Step 3：EXPLAIN 重点关注的 5 列

```sql
EXPLAIN SELECT ...
```

| 列           | 关注什么                                                     |
| ------------ | ------------------------------------------------------------ |
| **type**     | 这是核心——下面单独讲                                         |
| **key**      | 实际用上了哪个索引。**为 NULL 时是没走索引**——和 type=ALL 互相印证 |
| **rows**     | 估算扫描行数。**这才是真正的"快慢"指标**，type 是手段        |
| **filtered** | 估算过滤后的行数百分比。低 filtered + 高 rows = 索引选择性差 |
| **Extra**    | 红线警示：`Using filesort`、`Using temporary`、`Using where`（前两个尤其要警惕） |

Step 4：修复策略

| 问题            | 修复方向                                             |
| --------------- | ---------------------------------------------------- |
| type=ALL        | 加索引、改写让能命中索引                             |
| type=index      | 索引选择性差，列序不对                               |
| rows 大         | 加更选择性的索引、缩小范围                           |
| Using filesort  | 让 `ORDER BY` 列对齐索引顺序                         |
| Using temporary | 改写 `GROUP BY` / `DISTINCT` / `UNION`               |
| Using where     | 不一定是坏事（说明 server 层在做过滤），结合 rows 看 |

------

#### 第 3 层｜EXPLAIN type 类型全表（从好到坏）

按性能从高到低排，**这个顺序背下来比啥都管用**：

| Rank | type                             | 含义                                   | 触发条件                               | 典型 SQL                              |
| ---- | -------------------------------- | -------------------------------------- | -------------------------------------- | ------------------------------------- |
| 1    | **system**                       | 表只有 1 行（系统表/单行 const 表）    | MyISAM/Memory 单行表                   | 几乎遇不到                            |
| 2    | **const**                        | 单行扫描，PK/UK 命中                   | `WHERE pk = 1`                         | `WHERE id = 100`                      |
| 3    | **eq_ref**                       | JOIN 中，每行对方表必有唯一一行        | JOIN ON pk/uk                          | `A JOIN B ON A.b_id = B.id`           |
| 4    | **ref**                          | 非唯一索引等值匹配，可能返回多行       | `WHERE idx_col = ?`                    | KillEvaluation 大多数等值查询都是这个 |
| 5    | ref_or_null                      | 同 ref 但也匹配 NULL                   | `WHERE col = ? OR col IS NULL`         | 罕见                                  |
| 6    | index_merge                      | 多个单列索引合并                       | `WHERE a=? OR b=?` 各自有索引          | 经常是坏味道                          |
| 7    | unique_subquery / index_subquery | 子查询专用                             | `WHERE x IN (SELECT ...)`              | 现代优化器自动重写                    |
| 8    | **range**                        | 索引区间扫描                           | `>`、`<`、`BETWEEN`、`IN`、`LIKE 'x%'` | **下面单独讲**                        |
| 9    | **index**                        | 全索引扫描（不是全表，但扫整个索引树） | `SELECT idx_col FROM t` 没 WHERE       | 比 ALL 快但仍是扫描                   |
| 10   | **ALL**                          | 全表扫描                               | 没用索引                               | 大表上的红线                          |

几个关键边界

**`ref` vs `eq_ref` 的区别**：

- `eq_ref` 用的是 PK 或 UK，每个 JOIN 键**只可能返回 1 行**
- `ref` 用的是普通索引或 UK 的部分前缀，**可能返回多行**

**`range` vs `ref` 谁更好？** 不一定！

- `ref` 等值匹配后扫描 N 行
- `range` 区间扫描后扫描 M 行
- **谁扫得少谁就快**——看 rows 列，不是看 type 名字。

**`index` vs `ALL`**：

- `index` 扫的是索引树（更小），且通常是顺序 I/O
- `ALL` 扫的是数据表，包含所有列
- 在大表上 `index` 通常比 `ALL` 快 3-10 倍，但仍属于"扫描型"，不是"定位型"

------

#### 第 4 层｜range 单独深入

* range 是什么

> **range = 在索引 B+ 树上定位到一个区间起点，然后顺序扫描到区间终点。**

底层动作：

1. 优化器把 `WHERE` 条件转换成索引列的范围（一个或多个区间）
2. 在 B+ 树上**二分查找定位区间起点**——O(log n)
3. 沿叶子节点链表**顺序扫描到区间终点**——O(k)，k = 命中行数

* 哪些 SQL 会触发 range

| SQL 写法                      | 是否 range                                     |
| ----------------------------- | ---------------------------------------------- |
| `WHERE col > 100`             | ✅                                              |
| `WHERE col BETWEEN 1 AND 100` | ✅                                              |
| `WHERE col IN (1, 2, 3, ...)` | ✅（多个小区间合并）                            |
| `WHERE col LIKE 'abc%'`       | ✅（前缀匹配 = `col >= 'abc' AND col < 'abd'`） |
| `WHERE col LIKE '%abc'`       | ❌ 无法定位区间起点                             |
| `WHERE col != 100`            | ❌ "其他所有值"不是一个区间                     |
| `WHERE col IS NULL`           | 视情况，MySQL 可能用 ref，不是 range           |

* range 一定快吗？— 这是面试官最爱的反问

**不一定。** range 只代表"用了索引区间扫描"，**不代表行数少**：

| 场景                                         | type  | 实际行数  | 评价                      |
| -------------------------------------------- | ----- | --------- | ------------------------- |
| `WHERE id > 1000`（表有 1 亿行）             | range | 9999 万行 | **比 ALL 还慢**——还要回表 |
| `WHERE id > 99999999`（表有 1 亿行）         | range | 100 行    | 好得不能再好              |
| `WHERE created_at > NOW() - INTERVAL 1 HOUR` | range | 几万行    | 看场景                    |

**真正的优劣判断**：**`type = range` + `rows < 表总行数的 10%`** 才算优秀。否则要考虑：

- 缩小区间（增加更多过滤条件）
- 换更选择性的索引
- 反过来用 `ALL`（小表上 ALL 反而快——避免回表的随机 I/O）

range 的隐藏坑：复合索引中的"断链"

我前一题讲过：复合索引 `(a, b, c)`，查询 `WHERE a = ? AND b > ? AND c = ?`：

- type 看起来是 **range**
- key_len 看起来命中了 a 和 b
- 但 **c 不在索引定位里用上**——因为 b 范围扫描后 c 在叶子节点里乱序

这种情况 EXPLAIN 显示 type=range 但实际 rows 可能很大，**Extra 会有 `Using index condition`（ICP 介入帮忙过滤 c）但不能改变 c 没定位的事实**。

------

#### 第 5 层｜KillEvaluation 真实查询的 EXPLAIN 推演

假设建了 `idx_indicator_data(scenario_id, net_name, net_time, indicator_id)`（上一题推荐的索引）：

查询 1：[IndicatorDataServiceImpl:101-106](vscode-webview://1i4csngisab2k9m17phsr4nos9p1vjj8tb6i698esio1f1hk59as/KillEvaluation/src/main/java/com/example/killevaluation/service/impl/IndicatorDataServiceImpl.java#L101-L106)

```java
Db.lambdaQuery(IndicatorData.class)
    .eq(IndicatorData::getScenarioId, dto.getScenarioId())
    .eq(IndicatorData::getNetName,    dto.getNetName())
    .eq(IndicatorData::getNetTime,    dto.getNetTime())
    .in(IndicatorData::getIndicatorId, indicatorIds)   // ← IN 列表
    .list();
```

**预期 EXPLAIN**：

- `type = range`（IN 让最后一列变区间）
- `key = idx_indicator_data`
- `key_len` ≈ 4 个列的总字节数（命中所有 4 列）
- `rows` ≈ `indicatorIds.size()`（理想情况，每个 IN 值定位 1 行）
- `Extra = Using index condition`（ICP 帮忙在引擎层过滤）

**判断**：性能极佳。前 3 列等值精确定位到一个很小的子集，最后一列 IN 在子集内做范围跳跃。

------

#### 第 6 层｜面试官会怎么深挖

**攻击点 1：type=range 但 rows 很大怎么办？**

**正确思路**：缩小区间、加更选择性的索引、改写为多个等值查询。

**攻击点 2：什么是索引下推 ICP？**

**正确答案**：

- ICP（Index Condition Pushdown，MySQL 5.6+）
- 没有 ICP：引擎层根据索引拿到符合 a/b 的行 → server 层过滤 c → 大量回表
- 有 ICP：引擎层在扫描索引时就同时检查 c → **减少回表次数**
- EXPLAIN 里看到 `Using index condition` 就是 ICP 起作用
- KillEvaluation 的查询 1 就会触发 ICP——`IN` 列表在引擎层完成过滤

**攻击点 3：Using index 和 Using index condition 有什么区别？**

| Extra                 | 含义                                           |
| --------------------- | ---------------------------------------------- |
| Using index           | **覆盖索引**——查询的列全在索引里，不回表       |
| Using index condition | ICP 起作用，但仍要回表取其他列                 |
| Using where           | server 层做了 WHERE 过滤（很常见，不一定坏）   |
| Using temporary       | 用了临时表（GROUP BY / DISTINCT / UNION 触发） |
| Using filesort        | 排序无法利用索引，要额外排序                   |

**最理想的组合**：`type = ref + Extra = Using index`（覆盖索引等值查）。

**攻击点 4：MyBatis-Plus 的 `list()` 会让覆盖索引失效吗？**

**正确答案**：会。`list()` 默认 `SELECT *`，没法走覆盖索引。要享受覆盖索引必须 `.select(IndicatorData::getRawValue, IndicatorData::getNormalizedValue)` 显式列出字段。这是 ORM 项目共通的反模式。

**攻击点 5：如果 EXPLAIN 显示 type=ref 但接口还是慢，可能是什么原因？**

**正确答案**（这道题区分初级 / 高级）：

- **回表慢**：索引命中了但要回表读取其他列，且**结果集太大**（千万级）。解决：覆盖索引
- **锁等待**：EXPLAIN 不显示锁信息，要查 `performance_schema.events_waits_current`
- **网络传输**：返回了 `LongText` 大字段，查询本身快但传输慢
- **N+1 查询**：单条 SQL 快，但代码循环里执行了 1000 次
- **缓存未命中**：InnoDB Buffer Pool 装不下，每次都要从磁盘读
- **统计信息过时**：优化器估错行数，**选了错的索引**

攻击点 6：EXPLAIN ANALYZE 和 EXPLAIN 的差别？

**正确答案**：

- `EXPLAIN` 只显示**估算**的执行计划，不实际跑
- `EXPLAIN ANALYZE`（MySQL 8.0.18+）**真的执行**一遍，给出实际行数 / 时间 / loops
- **区别 = 估算 vs 实测**——估算行数差 10 倍很常见，实测才能确认优化器对不对
- DM8 没有 ANALYZE，但可以用 `SET STATISTIC ON` + 跑 SQL 看实际开销

**攻击点 7：你们项目实际遇到过什么慢 SQL？**

**真诚回答**（贴 KillEvaluation）：

- `fillIndicatorData` 的 `ne + isNull` 是潜在隐患（前文反模式 4）
- `IndicatorService.getSubTree` 如果是递归调用 N 层 SQL，会触发 N+1 问题；正确做法是一次性 `WHERE ancestor_id = ?` + 应用层组装
- 评估结果 `EvaluateItemVO` 树形结构如果用 SQL 递归 CTE 查（`WITH RECURSIVE`），DM8 上要验证支持度

------

#### 总结

> **慢 SQL 分析 = 慢日志找出来 → EXPLAIN 看 type/key/rows/Extra → 根据 type 反推优化方向**。 **type 是手段，rows 才是真相**——type=range 也可能扫千万行，type=ALL 在小表上也能跑得飞快。 KillEvaluation 里大多数等值查询会落在 `ref`（前缀等值）或 `range`（IN 列表），但 `fillIndicatorData` 的 `!= + IS NULL` 是已知的 `ALL` 反模式技术债。 国产化项目额外要注意：**DM8 不自动收集统计信息**，"索引存在但不走"是常见故障，要主动 `SP_TAB_STAT_INIT`。





### 过期时间如何设置

#### 第 1 层｜不设 TTL 的影响

> 默认情况下，Redis 中的 key **永久存在**，除非显式 `DEL` / `UNLINK` / 设置 TTL 后到期。

`SET key value`（不带 EX）= 持久 key，`TTL key` 返回 `-1`。

影响 1：内存堆积 + maxmemory 触发淘汰

Redis 是内存数据库，物理内存有上限。当内存达到 `maxmemory` 时：触发内存淘汰策略。

影响 2：业务残留 / 脏数据

KillEvaluation 实际例子：

- 用户 A 选了一组方案做评估 → 上下文写 `eva:eval:ctx`
- 用户 A 退出登录，没主动清 Redis
- 几个月后，运维查 Redis 发现 `eva:eval:ctx` 还在 → 不知道这是谁的、还有没有用

如果没有 TTL：这种数据只能靠人工运维清理，迟早积累成"垃圾场"。

正确做法：用 TTL 把"过期 = 失效"的语义编码到数据本身，不用业务代码主动清理。

影响 3：备份/持久化体积膨胀

- RDB：所有 key 都进快照，永久 key 全量保留 → 文件越来越大
- AOF：重写时把当前所有 key 写一遍，永久 key 占大头 → 重写慢
- 主从初始同步：传输 RDB 全量，永久 key 越多越慢
- 典型事故：从库初始同步时 RDB 文件 > 2GB，复制超时被主库断连，触发全量同步循环

#### 第 2 层｜项目中如何设置

**结合项目的标准答案**：

```java
public class TtlPolicy {
    // 基础 TTL
    public static final Duration CTX        = Duration.ofMinutes(30);
    public static final Duration EVAL_RAW   = Duration.ofHours(2);
    public static final Duration EVAL_TREE  = Duration.ofHours(2);
    public static final Duration SIM_SITU   = Duration.ofMinutes(10);

    /** TTL 加 ±10% 随机抖动，避免雪崩 */
    public static Duration jitter(Duration base) {
        long ms = base.toMillis();
        long delta = ThreadLocalRandom.current().nextLong(-ms / 10, ms / 10);
        return Duration.ofMillis(ms + delta);
    }
}
```

写入处一律 `set(key, value, TtlPolicy.jitter(TtlPolicy.EVAL_RAW))`。









### 大 key 该怎么存储？一开始无法确定是否为热点数据，如何区分是放进本地缓存还是 Redis？

#### 第 1 层｜大 Key 的存储与治理

什么算"大 key"（行业经验阈值）

| 数据结构                 | 警告阈值 | 危险阈值 |
| ------------------------ | -------- | -------- |
| String value             | > 10 KB  | > 100 KB |
| Hash 元素数              | > 1000   | > 5000   |
| List / Set / ZSet 元素数 | > 1000   | > 5000   |
| 单 Hash field 大小       | > 5 KB   | > 50 KB  |
| 单 key 总内存占用        | > 1 MB   | > 10 MB  |

**KillEvaluation 实测危险点**：

- `eva:eval:raw`（评估大树）：N 方案 × M 指标 × 每节点 6-8 个 SchemeData 字段 → **轻松上 MB**
- 5 方案 × 200 指标 = 1000 SchemeData 节点的 JSON 嵌套 → 实测 200KB-2MB

检测大 key 的工具

| 工具                          | 用法                                        | 评价                          |
| ----------------------------- | ------------------------------------------- | ----------------------------- |
| `redis-cli --bigkeys`         | 全表 SCAN + 抽样，每种类型给出 TOP 5 大 key | 生产可用，O(N) 扫描但低优先级 |
| `redis-cli --memkeys`（5.0+） | 直接看内存占用 TOP                          | 更准                          |
| `MEMORY USAGE key`            | 单个 key 字节数                             | 精确，但要先知道 key 名       |
| `redis-rdb-tools`             | 离线分析 RDB                                | 不影响线上，最详细            |
| `DEBUG OBJECT key`            | 看 serializedlength 等                      | 慎用，生产环境一般禁          |



#### 第 2 层｜大key存储手段

* 手段 1：拆分（最常用）

**字符串拆分**：

```java
原: eva:eval:raw      ← 2MB JSON
↓
拆: eva:eval:raw:meta  ← 100B 元信息（schema 数量、版本）
    eva:eval:raw:1    ← 200KB（前 50 个指标）
    eva:eval:raw:2    ← 200KB
    ...
```

**Hash 拆分**：用 Hash 拆，按 hash slot 映射：

```java
hash slot = crc(field) % 100
key = "user_data:" + slot
```

* 手段 2：压缩

```java
byte[] compressed = Snappy.compress(JSONUtil.toJsonStr(obj).getBytes());
redisTemplate.opsForValue().set(key, Base64.encode(compressed));
```

| 算法         | 压缩率 | 速度 | 适用         |
| ------------ | ------ | ---- | ------------ |
| **Snappy** ✅ | 50-70% | 极快 | 实时业务首选 |
| LZ4          | 50-70% | 更快 | 同上         |
| GZIP         | 70-85% | 慢   | 存储敏感场景 |
| Zstd         | 70-85% | 中等 | 现代选项     |

**注意**：Redis 7.0+ 的 `string` 类型本身有内部编码优化（embstr → raw），但只在 < 44 字节时压缩。**大对象必须应用层压缩**。

JSON 数据压缩率特别高（重复字符多）—— KillEvaluation 的评估树 JSON 用 Snappy 一般能压到原始大小的 **30-40%**。

* 手段 3：用 UNLINK 替代 DEL

```bash
# ❌ 阻塞主线程
DEL big_key

# ✅ 异步删除（4.0+）
UNLINK big_key
```

UNLINK 把删除工作交给后台线程，主线程立即返回。**这是治理大 key 删除阻塞的根治办法**。

```bash
redis-cli --scan --pattern 'situation' | xargs redis-cli unlink
```

#### 第 3 层｜热点未知时，L1 vs Redis 如何分？

3.1 两种思路：事前判断 vs 事后自适应

| 思路           | 代表方法                                           | 何时用       |
| -------------- | -------------------------------------------------- | ------------ |
| **事前判断**   | 按数据类型分（配置进 L1，业务进 Redis）            | 数据特征已知 |
| **事后自适应** | 访问统计 + 阈值升级；或交给缓存库自学（W-TinyLFU） | 热点不可预测 |

90% 的项目用第一种就够了——**"按数据语义分类"比"按访问频率分类"更稳定**。第二种是给那 10% 真的猜不出来的场景准备的。

3.2 事前判断的标准（5 个维度）

| 维度           | L1                       | Redis              |
| -------------- | ------------------------ | ------------------ |
| **对象大小**   | 小（< 10KB）             | 大（> 100KB）      |
| **变化频率**   | 低（配置类）             | 高（业务数据）     |
| **一致性需求** | 弱（可容忍秒级）         | 强（必须最新）     |
| **共享需求**   | 单节点用                 | 跨节点共享         |
| **加载成本**   | 高（DB 查表 / 公式计算） | 低（已经在 Redis） |

**5 个维度里 3 个偏 L1 就放 L1**，这是经验法则。

按这个表分 KillEvaluation 的数据：

| 数据                         | 维度 1 | 维度 2 | 维度 3 | 维度 4 | 维度 5 | 结论                |
| ---------------------------- | ------ | ------ | ------ | ------ | ------ | ------------------- |
| IndicatorStructure（指标树） | 小     | 低     | 弱     | 单     | 高     | **L1**              |
| AHPMatrix / TopsisWeight     | 小     | 低     | 弱     | 单     | 中     | **L1**              |
| IndicatorFormula             | 小     | 极低   | 弱     | 单     | 高     | **L1**              |
| 评估上下文                   | 小     | 中     | 强     | 单     | 中     | L1 / Redis 都行     |
| 评估大树                     | **大** | 高     | 强     | 单     | 极高   | **Redis**           |
| 拆分小树                     | 中     | 高     | 强     | 单     | 高     | **Redis**           |
| 仿真态势                     | 中     | 中     | 强     | 单     | 高     | Redis（已有，合理） |

**这就是为什么不需要"先看热点再决定"——绝大多数情况按数据特征就能定**。

3.3 事后自适应的几种方案

如果项目里有"猜不出热点"的场景（KillEvaluation 几乎没有，但通用项目有），看这几种：

方案 A：访问计数 + 阈值升级（手工自适应）

```java
private final ConcurrentHashMap<String, AtomicLong> accessCounter = new ConcurrentHashMap<>();
private final Cache<String, Object> l1 = Caffeine.newBuilder()
    .maximumSize(100)
    .expireAfterWrite(Duration.ofMinutes(10))
    .build();

public Object get(String key) {
    Object v = l1.getIfPresent(key);
    if (v != null) return v;
    
    v = redis.get(key);
    if (v == null) return null;
    
    long count = accessCounter.computeIfAbsent(key, k -> new AtomicLong()).incrementAndGet();
    if (count >= PROMOTE_THRESHOLD) {        // 比如 5 分钟内 10 次
        l1.put(key, v);                       // 升级到 L1
    }
    return v;
}
```

**优点**：可控、可观测、阈值可调 **缺点**：计数器本身占内存；需要定时清理冷 key

方案 B：用 Caffeine 的 W-TinyLFU（推荐）

```java
Caffeine.newBuilder()
    .maximumSize(1000)        // 设置容量上限
    .build();                  // W-TinyLFU 内置，无需额外代码
```

W-TinyLFU 的工作原理：

- 维护一个 Count-Min Sketch（小内存的频率估计结构）
- 新来 key vs 淘汰候选 key：频率高的留下
- "Window" + "Main" 两段结构，新 key 先进 Window 防止突发流量被立刻淘汰

实际效果：

- 比 LRU 命中率高 10-30%
- 内存开销极小（Count-Min Sketch 用几 KB 维护几万 key 的频率）
- 不需要业务代码判断热点——Caffeine 自己学

方案 C：Redis 4.0+ LFU 模式 + OBJECT FREQ

```
# redis.conf
maxmemory-policy allkeys-lfu
```

```java
Long freq = (Long) redisTemplate.execute(...,  "OBJECT", "FREQ", key);
if (freq >= HOT_THRESHOLD) {
    l1.put(key, value);
}
```

利用 Redis 自己的 LFU 计数（0-255 的对数化频率）判断热度。

**优点**：Redis 已经在算，免费搭车 **缺点**：要打开 LFU 模式，影响淘汰策略；FREQ 不能完全代表"应该上 L1"



### 使用了 SpringTask，如果是多实例服务部署

7 种主流方案全景

#### 方案 1：配置单点（最简陋）


`@ConditionalOnProperty` 控制 `@EnableScheduling` 是否生效，部署时只给一个实例开。

| 缺点 | **单点故障**：跑任务的实例挂了任务停摆；运维要记得"哪个实例是定时任务实例"，配置漂移风险 |
| 适用 | 内部工具、低可用性要求、临时方案                             |

#### 方案 2：数据库唯一索引锁

```sql
CREATE TABLE schedule_lock (
    task_name VARCHAR(64) NOT NULL,
    fire_time DATETIME NOT NULL,
    instance_id VARCHAR(64),
    PRIMARY KEY (task_name, fire_time)
);
```

```java
@Scheduled(cron = "...")
public void task() {
    try {
        jdbc.update("INSERT INTO schedule_lock(...) VALUES(?, ?, ?)", 
                    "cleanup", roundedFireTime(), instanceId);
        doWork();  // INSERT 成功的才执行
    } catch (DuplicateKeyException e) {

```

| 维度 | 评价                                                         |
| ---- | ------------------------------------------------------------ |

| 缺点 | DB 压力；需要定期清理旧锁记录；DB 故障时任务全停             |
| 适用 | 已有 DB + 任务低频（每小时甚至每天）                         |

#### 方案 3：Redis 分布式锁

```java
@Scheduled(cron = "...")
public void task() {
    String key = "lock:task:cleanup";
    Boolean acquired = redisTemplate.opsForValue()
            .setIfAbsent(key, instanceId, Duration.ofMinutes(10));
    if (!Boolean.TRUE.equals(acquired)) return;
    
    try {
        doWork();
    } finally {
        // Lua 脚本保证只删自己的锁
        unlockByValue(key, instanceId);
    }
}
```

| 维度 | 评价                                                  |
| ---- | ----------------------------------------------------- |
| 优点 | 性能好（O(1)）、引入门槛低、KillEvaluation 已有 Redis |
| 缺点 | **TTL 陷阱**（见第 4 层）、Redis 主从切换可能丢锁     |
| 适用 | 中小规模、能容忍极低概率重复执行                      |

**重要**：用 `Redisson` 比手写 SETNX 强很多——它内置 **WatchDog 看门狗自动续约**，避免 TTL 陷阱：

```java

if (lock.tryLock(0, -1, TimeUnit.SECONDS)) {  // -1 = 启用 WatchDog
    try { doWork(); } finally { lock.unlock(); }
}
```

### 分布式场景下，定时任务该如何实现？

**分布式定时任务的工业级答案就是"调度中心 + 执行器"两层架构**——XXL-Job / ElasticJob / PowerJob / SchedulerX 都遵循这套范式，本质上是把"调度的分布式协调"从业务代码里剥离出去，再加上**分片、编排、失败重试、可观测**等通用能力。 **自研路径**：调度中心集群（Raft 选主）+ 注册中心（执行器发现）+ MySQL（任务持久化）+ 时间轮（精准触发）+ 死信队列（失败重试）+ 全链路监控——能力完整、工作量不小。 **选型铁律**：业务量小用 Redisson + @Scheduled，中型上 XXL-Job，大型 / 需要 DAG 上 PowerJob，云原生 + 简单任务上 K8s CronJob——**绝大多数业务不要自研**。 KillEvaluation 当前无需求，未来加用 Redisson 即可，加到要 GUI 时再上 XXL-Job。





### Caffeine 本地缓存和 Redis 同时使用时，在分布式场景下 JVM 互相隔离，缓存一致性问题如何解决

#### 方案一

**Caffeine 只保留「短时间」且「弱一致性」数据（最推荐）**

这是最务实、成本最低的方案。不强求 Caffeine 中的数据与 Redis 完全一致，而是通过业务逻辑容忍短暂的不一致。

- 设置极短的 TTL（过期时间）：例如 5 秒、10 秒。
- 适用场景：配置信息、热门商品标题、用户昵称等对一致性要求不高的场景。
- **逻辑**：
  1. 读请求：先查 Caffeine，未命中则查 Redis，回填 Caffeine（TTL=5s）。
  2. 写请求：更新 Redis → 删除 Caffeine 中的 key（或等待其自然过期）。
  3. 在 5 秒内，不同实例可能读到旧数据。5 秒后所有实例数据一致。

> **一句话：用“短过期时间”来换取“最终一致性”，这是业界最通用的做法。**

------

#### 方案二

**使用 Redis Pub/Sub 主动失效（兼顾实时性）**

如果业务对一致性要求较高，不能容忍 5 秒的延迟，可以使用 **Redis 的发布订阅机制** 来主动通知所有服务实例，让它们主动失效自己的本地缓存。

- **原理**：
  1. 每个服务实例启动时，在 Redis 中订阅一个固定的频道（如 `cache:invalidate`）。
  2. 当某个实例修改了数据（更新 Redis 后），向该频道**发布一条消息**（内容为被修改的 key）。
  3. **所有订阅了该频道的实例**收到消息，立即删除自己 Caffeine 中的对应 key。
- **逻辑流程**：
  - 实例 A：更新 Redis → 发布消息 `invalidate:user:123`。
  - 实例 B、C：收到消息 → `caffeine.invalidate("user:123")` → 下次读请求会从 Redis 拉取最新数据。
- **优点**：
  - 不一致窗口缩短到**网络往返 + 消息解析的时间**（通常 < 10ms）。
- **缺点**：
  - Redis Pub/Sub **不保证消息必达**（如果实例断线重连，期间的消息会丢失）。
  - 需要一个**可靠的消息机制**来兜底（例如结合短 TTL，即使消息丢失，几秒后也会过期）。
