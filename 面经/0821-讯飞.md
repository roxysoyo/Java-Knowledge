## Answer

### A2-整体架构

**进入循环前**

用户敲了一句话回车之后，进主循环之前只做三件事：

第一，把这句话设成当前任务摘要，因为后面每一轮都要提醒模型"你在做的是这件事"。

第二，进对话历史，并且立刻落盘。

第三，给这次运行建一个独立的档案目录，写下第一份状态快照。从这一刻开始，这次运行的每一个事件都会往这个目录里追加。

**进入循环**

1. 重新组装上下文。

- 这里我想强调一个设计决策，因为整个架构的下半部分都是从它长出来的：每一轮的上下文都是重新组装的，不是在上一轮后面追加。

- 组装之前会先做两个检查：工作区的指纹变没变，变了才重建那段稳定内容；上一个断点还算不算数，也就是当时记下的关键文件现在有没有被改过、运行配置有没有换过。如果发现失效了，会当场补一个新断点，然后才组上下文。

2. 调模型，然后解析。

- 调用之前会看后端支不支持前缀缓存，支持才把稳定段的指纹作为缓存键带上去。拿回文本之后立刻解析，结果只有三种：一个工具调用、一个最终答案，或者第三种——解析不出来。

3. 按三种结果分三条路走。

- 如果是工具调用，就进执行闸门。危险工具会在执行前后各做一次工作区快照，比对出这次到底改了哪些文件。执行完之后，结果会同时流向三个地方：完整结果进历史，少量高价值的事实提炼进工作记忆，执行的元信息进事件流。然后建一个断点，回到循环顶部重新组上下文。

- 如果是解析不出来，我不会直接失败，而是生成一条明确的提示告诉模型格式错在哪，把这条提示当成模型自己说过的话记进历史，让它下一轮看得见。这条路只消耗重试次数，不消耗步数。

- 如果是最终答案，就收尾：记进历史、标记任务完成、判断这次要不要往长期记忆里沉淀东西、建最后一个断点、写一份运行报告，然后返回给用户打印出来。

4. 每一步都留痕。

- 上面每一个动作我都会往事件流里追加一条记录。所以这次运行结束之后，把那个文件从头读到尾，就是这次运行的完整故事：这一轮上下文怎么拼的、为什么被裁剪、缓存命没命中、工具改了哪些文件、为什么停下来。



### A3-shell命令处理

==第一段：先交代威胁模型（这段不能省）==

> 讲安全机制之前我想先说威胁模型，因为不说威胁模型的安全设计都是在堆 checklist。
>
> 这个工具的威胁模型是：**防模型犯错，不防模型作恶，也不防用户作恶。**
>
> 用户本来就坐在自己的终端前面，他有完整的 shell 权限，我防他没有意义。我要防的是模型幻觉出一条破坏性命令、陷进循环反复执行、或者把不该读的东西读出来。这是一个**误操作模型**，不是**对抗模型**。
>
> 威胁模型定下来之后，很多设计选择就是可推导的了。

==第二段：为什么不做内容判定==

> 如果要做内容判定，本质上是要回答"执行这段字符串会不会产生破坏性副作用"。这是个不可判定问题，而且在 coding agent 这个场景里，绕过它甚至不需要刻意——**日常正常用法就已经绕过去了。**
>
> 我举四类，从最常见的开始：
>
> **第一类，命令无害但目标是模型自己写的。**刚才说的 `pytest` 是一个，`make test` 是一个，`npm install` 触发 postinstall 也是一个。命令字符串永远长得人畜无害，实际执行的是模型上一步刚落盘的代码。这一类在 coding agent 里不是边缘情况，**是主流程**。
>
> **第二类，换一门语言。**你把 `rm` 加进黑名单，模型写 `python -c "import shutil; shutil.rmtree(...)"`。你把 `shutil` 也加进去，还有 `os.remove`、`find -delete`、`truncate`。你在黑名单里追的是无穷集合。
>
> **第三类，shell 自己的展开能力。**变量展开、命令替换、base64 解码之后管进 sh。你要挡这些，等于要在执行前把 shell 的求值语义实现一遍。
>
> **第四类，语义之外的破坏。**`git reset --hard`、`git push --force`、`chmod -R`——这些命令一个危险符号都没有，但后果可能比 `rm` 还严重。
>
> 所以黑名单的真实作用是**给人一种安全感**，而它挡住的恰好是最笨的那种攻击。我不想要一个只能挡笨错误、但让我误以为自己安全了的机制。

这四类要说得快、说得具体。**具体的反例是这道题唯一的硬通货**，泛泛说"黑名单会被绕过"没有说服力。

==第三段：那我实际做了什么——三道==

> 判定这条路走不通，我就把赌注转移到另外三个地方。

> **第一道，把判定权交给人，而不是交给代码。**
>
> shell 和写文件、改文件一起被静态标记为高危。高危工具在执行前必须过审批，策略有三档：每次问、全自动、一律拒绝。派出去的子 agent 强制走"一律拒绝"这档，所以子 agent 从设计上就不可能执行任何写操作。
>
> 关键点是：**审批发生在参数校验之后、执行之前**，用户看到的是最终要执行的完整命令原文，不是模型的自然语言描述。中间没有任何改写环节，所见即所执行。

> **第二道，能力最小化——让它就算跑起来也够不着重要的东西。**
>
> 这道里我最看重的是**环境变量白名单**。子进程拿到的环境不是从父进程继承来的，是我按白名单**重新构造**的，只有十来个变量。这意味着**所有 API key 从一开始就不在那个进程的环境里**。就算模型执行 `env` 或者 `echo $ANTHROPIC_API_KEY`，它也拿不到东西——不是因为我拦住了，是因为那里根本没有。
>
> 另外还有超时上限、输出长度上限，以及一个更粗暴的开关：**工具白名单**。跑评测的时候我会直接不给某些任务 shell 这个工具，模型连调用它的机会都没有。这是最有效的一层，因为它不依赖任何判定。

> **第三道，事后可观测——承认我拦不住，但要保证我知道发生了什么。**
>
> 每个高危工具执行前后，我会对工作区做一次内容指纹快照，比对出这次到底改了哪些文件。这带来一个我认为很重要的中间状态：**命令失败了，但文件已经改了一半。**
>
> 光看返回码只有"成功"和"失败"两种，比对快照才能得到第三种——半成功。这三种在恢复的时候处理完全不同：成功可以继续，失败可以直接重试，**半成功必须停下来让人看一眼**。我把它单独标成一个状态，并且写进事件流。
>
> 加上密钥脱敏，事件流和报告里不会残留任何真实密钥值。

==第四段：主动交边界（这段是加分的关键）==

> 我想主动说清楚这套机制**没有**做到什么，因为我不希望它听起来比实际更强。
>
> **第一，工作目录锚定只是起点，不是围墙。**我给文件类工具做了严格的路径锚定，任何路径都必须落在仓库内，软链接也挡。但 shell 不受这个保护——我只是把子进程的起始目录设在仓库根，命令里写一个绝对路径或者 `cd ..` 就出去了。**这两层保护强度完全不同，我不会把它们混在一起讲。**
>
> **第二，快照只覆盖工作区内部**，仓库外的改动我看不见。
>
> **第三，全自动那档等于放弃第一道防线**，它是给评测和可信任务用的，不是给日常用的。
>
> **第四，超时只能保证我不被挂住，不能保证清理干净。**后台派生出去的进程可能活过超时。
>
> 这四条的共同根源是同一件事：**我做的是进程内的策略约束，不是操作系统级的隔离。**真正要解决，正确答案是容器或沙箱——只读挂载、独立文件系统、网络隔离、系统调用过滤。我没做，是因为这是个本地单人工具，威胁模型是误操作不是恶意，上沙箱的复杂度和收益不匹配。**但我清楚这条线画在哪。**



### A4-测试用例

测一个 agent，第一个问题不是"测什么"，是**"怎么让它可测"**——因为它的核心依赖是一个不确定的模型。同样的输入，模型两次输出可能完全不同，这样的系统写不出稳定断言。

我的做法是**把模型换成一个脚本演员**。测试里注入一个假的模型客户端，它不联网，只是按顺序吐出我事先写好的输出。这样整个控制循环就从不确定系统变成了确定系统。

换掉之后，每个测试都变成同一个句式：**"给定模型说了这句话，harness 应该怎么反应。"**——它该执行工具吗？该拒绝吗？该记什么？该在哪停下来？这些全都是可以精确断言的。

在这个地基上我分了四层：公共接口契约、安全不变量、端到端行为、模块单元。

==第一段：地基——注入一个确定性的模型==

> 假模型客户端的接口和真的完全一样，构造的时候传一个输出列表进去，每次调用弹出一个。所以我可以**编排一整段对话**：
>
> 第一条让它返回一个读文件的工具调用，第二条让它返回最终答案——这就测了一次完整的"工具后收尾"。
>
> 第一条故意返回一段格式错误的东西，第二条返回正常答案——这就测了"模型说胡话之后能不能自己恢复"。
>
> 前三条全是格式错误——这就测了重试预算耗尽之后的停机路径。
>
> **关键是这些编排是可复现的。**没有它，agent 的测试只能靠跑很多次看统计，那不是测试，那是评测。

==第二段：只在两个地方 mock==

> 我给自己定了一条规则：**mock 只允许出现在系统边界上，内部逻辑一律不 mock。**
>
> 实际上只有两处。一处是 HTTP，测各个模型后端适配的时候把网络请求拦下来。另一处是人工审批的那个输入。
>
> 除此之外**文件系统我用的是真的**——每个测试建一个真实的临时目录当仓库。所以测路径逃逸的时候，我是真的在临时目录外面建一个文件，再真的建一个软链接指过去，然后断言工具拒绝了它。
>
> 这一点我认为很重要：**路径解析、软链接、文件内容指纹这些东西，mock 掉之后测的就是我的假设，不是系统的真实行为。**而这几个恰好是安全边界所在的位置，是最不能测假的地方。

==第三段：四层分别在防什么==

> **第一层，公共接口契约。**
>
> 这一层的特点是**大量反向断言**——断言不该存在的东西确实不存在。比如重构完之后，我会断言旧的类名不在包的导出列表里、旧的模块文件在磁盘上确实已经删掉了、打包配置里确实声明了要收集子包。
>
> 这一层防的是**重构回退**：改了一半、旧入口还活着、或者拆了包但打包的时候没带上——这几种问题不会让任何功能测试失败，但会在别人安装的时候炸。
>
> **第二层，安全不变量。**
>
> 每一条安全边界一个测试，而且这一层的测试是**允许重复覆盖**的。路径逃逸、软链接绕出去、审批拒绝、环境变量白名单、子 agent 的深度限制、子 agent 强制只读、密钥在事件流和报告里被脱敏。
>
> 这一层我单独放一个文件，是因为它的语义和别的层不一样：**别的层是"功能对不对"，这一层是"这条线永远不许被跨过"。**任何人改代码碰红了这个文件，都该停下来想一想，而不是顺手改断言。
>
> **第三层，端到端行为。**这层最大，从对外那个入口进去，断言四个地方：对话历史、工作记忆、任务状态、落盘的运行工件。
>
> **第四层，模块单元测试。**上下文组装、记忆、断点、工具执行这些各自单独测。
>
> 上下文这块的测法有点意思：我**故意把内容撑到超预算**——把稳定段填成几百个重复字符，塞三条超长笔记——然后断言削减的顺序是对的、用户请求那段一个字没少。**光测"正常情况能拼出来"是没用的，预算逻辑只有在超预算的时候才存在。**

==第四段：几个具体手法==

> 有几个我自己觉得比较有用的做法：
>
> **测试名写成需求句子。**比如"恢复的时候如果文件已经被改过，应该让旧摘要失效并标记为部分失效"。测试列表打印出来基本就是一份行为规格。
>
> **断言"不该发生的事"。\**举个例子，参数非法的时候我会断言\**审批提示压根没有被调用过**。这测的不是结果，是**顺序**——校验必须在审批之前。如果哪天有人把顺序换了，功能表现上看不出区别，但这个测试会响。
>
> **评测器本身也要被测。**比如断言每个任务确实用的是新拷贝的仓库副本、断言路径锚定在副本里而不是原仓库、断言失败分类的计数是对的。**因为如果评测代码本身有 bug，我拿到的所有数字都是假的。**

==第五段：主动交边界==

> 这套东西的不足我也说一下。
>
> **没有 CI**（Continuous Integration），全靠本地跑。这是这个项目最该补的一项。
>
> **没有覆盖率门槛**，我是按风险手工决定测哪里的，安全和状态恢复覆盖得密，展示层基本没测。
>
> **测试辅助函数在几个文件里是重复的**，应该抽成公共 fixture。
>
> 还有一条我觉得是真正的设计缺陷：**很多断言是直接匹配错误信息字符串的**。这意味着改一句提示文案就会碎掉一批测试。正确做法是断言结构化的错误码——**我的工具执行返回值里其实已经带了错误码字段，只是测试没用上。**这个我知道该怎么改，只是还没动。



我举个具体的。测一次工具调用，我传给假模型的是一个两条的列表：第一条是一个读文件的工具调用，第二条是最终答案。调用一次 `ask`，然后断言三件事——返回值对不对、历史里有没有那次工具调用、记忆里有没有记下这个文件。

这个列表就是剧本。**改剧本就能换场景**：第一条改成格式错误的，测的就是模型说胡话之后能不能自愈；前面塞两条空回复同时把步数预算压到 1，测的就是重试有没有偷吃步数预算。

还有一个反向用法：假客户端会把每轮收到的 prompt 也存下来，所以我可以反过来断言**模型到底看到了什么**。测上下文压缩的时候，我在历史里埋两个可识别的字符串，跑完检查最后那份 prompt 里近的还在、远的已经被压掉了。



我不会用测试数量来论证覆盖——134 条测试完全可能全在测同一个函数。

我的方法是**从规格倒推，不从代码正推**。看着代码写测试，只能覆盖"代码现在做了什么"，覆盖不了"本该做什么但没做"。

具体做法是：**凡是有枚举状态的地方，每个值至少一条测试。恢复状态五个、停机原因、工具错误码、安全事件类型，这些在我代码里都是常量表，所以这件事可以自动化**——我可以写一条测试，遍历所有状态常量，断言每个都在测试代码里出现过。新增一个状态却忘了配测试，CI 直接响。**行覆盖率做不到这个，加一个枚举值它纹丝不动。**





### A5-ai使用

我不回避这个问题——**代码量上 AI 参与很多，我用它写了大量实现和文档。**

但我想把分界线说清楚：**AI 写的是实现，我定的是约束。**

具体来说，架构怎么切、边界划在哪、哪些东西刻意不做，这些是我定的，而且我能说清每一处的理由，包括为什么不选另一个方案。安全边界和测试断言的意图，是我逐条过的。评测数字的口径边界，是我自己划的——**哪些结论不能往外推，这件事 AI 不会主动告诉我。**

而且我觉得这个项目有点特殊：**它本身就是一个 coding agent。我用 coding agent 来做 coding agent，这个过程给了我最直接的一手体感——我在项目里解决的那几个问题，全都是我自己用这类工具时被卡住过的。**



具体分工上：

**AI 主要承担实现和文档。**样板代码、数据类、格式化输出、重复的测试骨架，这些交出去效率高很多。

**我承担的是决策和验收。**我举三个 AI 帮不上忙的例子：

**第一，上下文超预算的时候先削哪一段。**顺序是先削按问题召回的笔记，再削历史，最后才动稳定段，用户请求永远不削。这个顺序背后是一个判断——**最近发生的事比很久以前的事更影响下一步决策**。这是我定的，而且我把它硬编码成常量而不是每次现算，因为现算的话行为就不可复现了。

**第二，shell 命令我决定不做内容黑名单。**这个决定是"不做某件事"，AI 默认会倾向于给你写一个黑名单，因为那看起来更负责。我判断那条路走不通，理由是命令的危险性不在命令字符串里，在工作区状态里。

**第三，评测报告里那份口径边界。**我明确写了哪些指标能拿出去说、哪些只能内部看、哪些结论不能混在一起写。**这是给自己设限，不是加功能**，不会有任何工具主动建议你这么做。

至于验收，我的标准是一条：**这个仓库里任何一段代码，你指着问我为什么这么写，我要答得上来，包括当时排除掉的方案是什么。**答不上来的地方，我要么重写要么删掉。
